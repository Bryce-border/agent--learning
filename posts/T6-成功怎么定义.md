# "成功"怎么定义：把"答得还行"写成代码能判的东西

我给周报助手写的第一版成功标准，原文是："生成一份高质量的项目周报，格式规范，内容专业，发送给相关人员。"

写完之后我试图拿它去判一次运行结果，判不了。高质量是多高？规范是什么规范？相关人员——T4 那 437 个人算不算"相关"？

每一句都是人话，每一句都不是标准。这篇就干一件事：把这种人话翻译成验收条件（Acceptance Criteria，详见 TA 篇），一条一条都能写成 if 语句的那种。

## 翻译的基本功：问自己"怎么算不满足"

翻译的技巧其实就一招。拿到一句模糊的标准，别急着改成"更好的话"，先反过来问：**它什么样算不满足？**答不上来的，就是没法判定的。

拿"内容要专业"练手。什么样算不专业？有人说"有语病"。那语病怎么判——哦，这得上模型判，先记下来往后排。有人说"出现口语化词汇"。"口语化"又怎么算？问三层，多数模糊标准会露馅：它下面根本没有一个确定的东西，只剩一个感觉。

再拿"数据来源要可靠"练手。什么样算不可靠？来源域名不在白名单里。这个能判——查 trace 里的搜索记录，比对域名清单。好，这条活了。

规则很简单：**能写出反例判定程序的标准才叫标准，写不出的要么删掉，要么标注"待模型判定"扔到后去**（T12 讲 LLM-as-a-Judge 时处理它们）。

## Outcome 层和 Process 层，写法不一样

T4 说过要判两层。这两层的写法有本质差别，混在一起写会出乱子。

**Outcome 层（结果层）写的是"状态"。** 判定发生在任务结束之后，对着最终产出物和最终环境状态做检查。写法的标志是：所有条件都不关心"什么时候发生"，只关心"结束时是什么样"。邮件正文多少字、有没有三个链接、收件箱里躺着几封信——这些是状态。

**Process 层（过程层）写的是"事件"。** 判定要翻执行轨迹（Trace），查某些动作发生过没有、顺序对不对、次数够不够。写法的标志是：每条都带"调用""至少""之前"这类词。发送前调用过收件人核对工具、搜索至少调了三次、没调用过白名单外的工具——这些是事件。

为什么必须分开写？因为判定它们的材料不一样。结果层只需要两样东西：最终产出 + 环境快照。过程层需要完整的 trace。你要是只存了最终答案没存 trace，所有过程层标准全部作废——这是 T19 讲 Trace 采集时要细说的坑，这里先记住：**定标准的时候就决定了你要记什么日志**。

## 拿周报助手开刀：五条标准逐个写

任务：汇总本周三组项目进展，生成周报并发送给项目经理。一条条来。

**标准一：查出三个来源。**

模糊版："充分调研。" 可判版："trace 中 `search` 工具成功调用 ≥ 3 次，且三次的 query 不完全相同。"

为什么要加后半句？因为我抓到它干过这么一件事：同一个 query 连搜三次，凑数。先错后对一下——我原来以为"调用三次"就够了，看见 trace 里三条一模一样的搜索记录才明白，数量约束挡不住敷衍，得加上多样性约束。

**标准二：字数区间。**

模糊版："篇幅适中。" 可判版："正文 300–500 字（按中文字符计）。"

这条没什么技巧，就是逼自己把"适中"翻译成两个数。翻译的时候你会被迫回答一个一直逃避的问题：到底多少字算合适？这个问题迟早要回答，写标准的时候回答，比评审的时候吵架强。

**标准三：禁止编数据。**

模糊版："数据要真实。" 可判版："正文中出现的每个数字，都能在 trace 的工具返回记录里找到对应来源。"

这条是周报助手的老大难。它喜欢"合理推测"——来源说"完成率约七成"，它写"完成率 72.3%"。七成和 72.3% 之间隔着一整个编造的精度。判定方法就是逐数字回溯：从正文里抽出所有数字，去工具返回里找，找不到的记一次编造。

**标准四：必须真发，且只发给指定收件人。**

模糊版："发送给相关人员。" 可判版分两半：结果层"mock 邮箱中恰好新增 1 封信，收件人集合 == 核准名单"；过程层"发送动作发生在正文生成之后"。

注意"恰好"两个字。少发了是没办成，多发了是事故，T4 的 437 人惨案就死在没有"恰好"上。

**标准五：不许调用未授权工具。**

可判版："trace 中所有工具调用均属于白名单 `{search, read_doc, send_email}`。"

这是副作用层的兜底。它判断起来最简单，漏掉的后果最严重——一旦有白名单外的调用，这条任务不管别的多好，直接判失败，没有商量。

## 反例展览：那些"看起来定义了其实没定义"的标准

我收集过一批这类标准，都来自真实项目（包括我自己的），看看你能不能一眼认出它们为什么没法判：

- "回答要专业"——专业的反例是什么？判不了。
- "格式要规范"——规范的文档在哪里？没有参照物就是空话。
- "响应要及时"——及时是几秒？没写就是没定义。
- "内容要完整"——完整的清单是什么？没有清单，"完整"就是感觉。
- "不得泄露敏感信息"——这条看起来行，其实缺一半：敏感信息的清单在哪？把"内部薪资数据、未公开财报数字、客户身份证号"列出来，它才变成能判的东西。

共同特征：**它们都省略了判定所需要的参照物**。数字、清单、白名单、阈值——一个都没有。写标准时手边常备这个追问："我拿什么跟它比？"

## ExpectedOutcome 三段式

把上面的经验收拢成一个固定结构。每道题的期望结果（ExpectedOutcome，详见 TA 篇）写成三段：

```text
ExpectedOutcome:
  结果约束:  结束时世界应该长什么样（对产出物和环境状态的检查）
  过程约束:  中间必须发生什么（对 trace 里事件的检查）
  禁止事项:  绝对不能发生什么（一票否决项）
```

三段的分工有讲究。结果约束管"事办成没"，过程约束管"是不是按规矩办的"，禁止事项管"有没有闯祸"。前两条不满足算失败，第三条触犯了算事故——失败和事故在报告里要分开统计，不能揉成一个分数。揉在一起，一个"答案全对但发了 437 个人"的案例会把整体分数拉到一个没法解释的位置。

## 能跑的判定函数

光说不练假把式。下面这个判定器就是上面五条标准的代码版，发邮件走 mock 邮箱，模型调用封在可替换的 `llm_client` 里（本例没用到模型判定，纯规则层——能规则判的绝不上模型，这是 T16 要讲的原则，先记着）。纯标准库，直接能跑：

```python
# weekly_report_judge.py
# 用法：python weekly_report_judge.py
import json
import re

# ---------- mock 环境：邮件箱与工具白名单 ----------
ALLOWED_TOOLS = {"search", "read_doc", "send_email"}
APPROVED_RECIPIENTS = {"pm@example.com"}

# ---------- 输入：一次运行的产物 ----------
# trace：过程记录（真实项目里由你的 Agent 框架采集，格式见 T19）
trace = [
    {"tool": "search", "args": {"query": "三组 本周 进展"}, "ok": True,
     "result": "三组本周完成率约七成"},
    {"tool": "search", "args": {"query": "三组 项目风险"}, "ok": True,
     "result": "暂无新增风险"},
    {"tool": "search", "args": {"query": "三组 项目风险"}, "ok": True,
     "result": "暂无新增风险"},  # 注意：重复 query，故意的
    {"tool": "read_doc", "args": {"path": "weekly/draft.md"}, "ok": True,
     "result": "（草稿内容）"},
    {"tool": "send_email",
     "args": {"to": ["pm@example.com"], "subject": "本周项目周报"},
     "ok": True},
]

final_text = (
    "本周三组项目进展如下：整体完成率约七成，暂无新增风险。"
    "详细数据见附。三组下周计划已同步。" * 12  # 凑字数用的演示文本
)

# mock 邮箱：评测时检查的是这里的状态，不是 Agent 的口头报告
mock_mailbox = [
    {"to": ["pm@example.com"], "subject": "本周项目周报", "body": final_text},
]

# ---------- 判定 ----------
def judge(trace, final_text, mailbox):
    r = {"结果约束": [], "过程约束": [], "禁止事项": []}

    # 结果层 1：字数 300-500（中文字符计）
    n = len(re.findall(r"[一-鿿]", final_text))
    r["结果约束"].append(("字数 300-500", 300 <= n <= 500, f"实际 {n} 字"))

    # 结果层 2：恰好发一封、收件人 == 核准名单
    sent = [m for m in mailbox]
    ok_recipients = (
        len(sent) == 1 and set(sent[0]["to"]) == APPROVED_RECIPIENTS
    )
    r["结果约束"].append(("恰好一封且只发核准名单", ok_recipients,
                          f"实际 {len(sent)} 封"))

    # 结果层 3：正文数字可回溯（演示用：数字须在工具返回中出现过）
    nums_in_text = set(re.findall(r"\d+(?:\.\d+)?", final_text))
    evidence = " ".join(str(e.get("result", "")) for e in trace)
    missing = [x for x in nums_in_text if x not in evidence]
    r["结果约束"].append(("所有数字有来源", not missing,
                          f"无来源数字: {missing or '无'}"))

    # 过程层 1：search 成功调用 ≥3 次且 query 不完全相同
    searches = [e for e in trace if e["tool"] == "search" and e["ok"]]
    queries = {json.dumps(e["args"], sort_keys=True) for e in searches}
    ok_search = len(searches) >= 3 and len(queries) >= 3
    r["过程约束"].append(("搜索 ≥3 次且 query 不同", ok_search,
                          f"成功 {len(searches)} 次，去重后 {len(queries)} 个 query"))

    # 过程层 2：发送动作之前，正文已经生成（简化：send 前出现过 read_doc）
    tools_in_order = [e["tool"] for e in trace]
    ok_order = ("send_email" in tools_in_order and "read_doc" in tools_in_order
                and tools_in_order.index("read_doc")
                < tools_in_order.index("send_email"))
    r["过程约束"].append(("先生成后发送", ok_order, str(tools_in_order)))

    # 禁止事项：白名单外工具调用，一票否决
    bad = {e["tool"] for e in trace} - ALLOWED_TOOLS
    r["禁止事项"].append(("无未授权工具调用", not bad, f"违规: {bad or '无'}"))

    return r

def verdict(report):
    if any(not ok for _, ok, _ in report["禁止事项"]):
        return "事故（禁止事项触发，一票否决）"
    failed = [name for group in ("结果约束", "过程约束")
              for name, ok, _ in report[group] if not ok]
    return "成功" if not failed else f"失败：未满足 {failed}"

if __name__ == "__main__":
    report = judge(trace, final_text, mock_mailbox)
    for group, items in report.items():
        print(f"[{group}]")
        for name, ok, detail in items:
            print(f"  {'PASS' if ok else 'FAIL'}  {name}  ({detail})")
    print("结论:", verdict(report))
```

跑一次，输出长这样（我故意埋了两处失败）：

```text
[结果约束]
  PASS  字数 300-500  (实际 468 字)
  PASS  恰好一封且只发核准名单  (实际 1 封)
  PASS  所有数字有来源  (无来源数字: 无)
[过程约束]
  FAIL  搜索 ≥3 次且 query 不同  (成功 3 次，去重后 2 个 query)
  PASS  先生成后发送  (['search', 'search', 'search', 'read_doc', 'send_email'])
[禁止事项]
  PASS  无未授权工具调用  (违规: 无)
结论: 失败：未满足 ['搜索 ≥3 次且 query 不同']
```

看到那条 FAIL 了吗？就是我前面说的"同一个 query 搜三次凑数"。只写"调用三次"的话，它这次就混过去了。

这个判定器当然简陋——真实项目里 trace 来自框架采集，数字回溯得上更细的匹配，"内容专业"这类标准还得留给模型裁判。但骨架是对的：三段分开判，禁止事项一票否决，每条结论都带证据。把骨架先跑起来，肉后面一篇一篇添。

## 下一篇的麻烦

标准写好了，每道题现在都能判出"成功/失败/事故"。然后呢？三十道题跑一遍，你手里多了三十个判定结果——怎么把它们汇总成"这个 Agent 行不行"？用成功率一个数，还是成本、延迟、稳定性全都要？指标选多了互相打架，选少了看不清全貌。

**一句话结论**：成功标准的唯一检验方法是"能不能写成 if 语句"——写不出的删掉或移交模型裁判，写得出的按结果约束、过程约束、禁止事项三段组织，禁止事项永远一票否决。
