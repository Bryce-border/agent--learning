# 你的 Agent "行不行"，到底在问什么

"它现在准确率多少？"

会议室里这句话扔过来，我愣了大概三秒。手底下这个东西跑了三周：能联网搜、能读内部文档、能自己写一封邮件发出去，内部我们都叫它周报助手。demo 那天演示得很顺，老板还点了两下头。可这一问，我发现自己嘴边只剩"挺好用的"四个字，而那四个字在一屋子等着拍板的人耳朵里，等于零。

那三秒里真正卡住我的其实不是"它准不准"。是另一件事——你说的"行"，到底是哪一种行。

## 一句"行不行"，其实是四句话

**第一种：几个方案摆面前，挑一个。**

自研的、套框架的、直接接大厂 API 的，三个都跑通了 demo，现在要留一个。这时候问的是横向可比：三个东西必须在同一批题上、按同一套判定标准、在同一天跑完，出来的数字才有排序的意义。拿 A 在自家 20 道题上的成绩去跟 B 在公开榜单上的成绩比，那是车祸现场。

周报助手也走过这一步。写邮件这块，是让模型直接吐正文，还是先列提纲再写？两边都跑完 30 道题才发现：短邮件上直接吐的更好，长邮件上先提纲的那个明显更像人写的。这个结论只能来自同一批题。

**第二种：这周的改动，到底有没有用。**

这是最常撞上的场景。改了一句 system prompt，换了个检索阈值，把工具描述重写了一遍——然后呢？

它问的是纵向可比：除了这一处改动，别的一切都得钉死。同一批题、同一个模型版本、同一份文档快照。你既换了模型又改了 prompt，跑出来涨了 5 个点，谁也说不清这 5 个点算谁的。

**第三种：能不能放出去。**

前两个场景关心平均分，这个场景关心最坏的那几个。周报助手最大的风险不在写错，在于它真的会按发送键。平时分数再高，只要有一条任务里它把草稿发给了全公司，上线这件事就得重新谈。这里要的从来不是"平均准确率 85%"，而是"过去三个月，发错人的次数是 0"。

**第四种：对外交代它是可靠的。**

老板、客户、隔壁部门。他们不参与你的迭代，只看结论。

他们真正会追问的是两句话：这数字是怎么来的？换个人照着跑一遍，还是一样吗？你说 85%，他问在哪批题上；你说在自家 50 道题上，他问那 50 道题谁出的。答不上来，85% 就只是个气氛。

四个场景，四种问法。它们连"要多少样本""要精确到什么程度""允不允许花钱"都不一样。

## 一个准确率数字，糊弄不了四个人

我一开始以为这事挺简单：攒 100 道题，跑一遍，算个准确率，四个场景共用，一劳永逸。

（我当时也这么以为。）

真动手，第一个场景就崩了。为了选型，三个方案都得跑同一批题，其中一个是外部 API、按次计费，100 道题跑三遍，账单先到了。第二个场景也崩：迭代是每周一次，一周的改动只影响 100 道题里的 6 道，剩下 94 道纯属烧钱，还把那 6 道的变化稀释到看不见。

说白了，问题根本不是"要不要评测"，是"为这个问题，值得花多少评测"。

这就是为什么我不建议你一上来就搭一套大而全的评测平台。它贵，它慢，而且在你还没想清楚要回答哪个问题之前，搭出来的东西大概率答非所问。

## 不管哪种场景，这四样都得有

场景可以分，零件是共用的。缺一样，跑出来的数字就是废的。

**① 任务集（Task Suite，详见 TA 篇）**

一批题。题从哪儿来、覆盖什么场景、难度怎么分，那是 T5 的事。眼下你只要记住一条：题集不固定，任何数字都不可比。

**② 成功判定标准（Success Criterion，详见 TA 篇）**

"答对了"这三个字必须能被执行。周报助手有一道题是"帮我总结上周销售数据并发给张三"，判什么？邮件正文里出现了上周的三个关键数字？收件人是张三且只有张三？附件齐全？这些得先写清楚，不然每次跑完都靠肉眼扫，扫到第三次你就不扫了。

**③ 指标（Metric，详见 TA 篇）**

成功率、成本、延迟、稳定性。别贪多，这是 T7 的活。

**④ 可复现的运行环境**

这第四个最容易被跳过，也最致命。同一个 Agent，早上 90 分，下午 70 分，代码一行没改——因为网上的页面变了、接口超时了、模型那边悄悄更新了。

四件套的最小版本长这样：

```python
# 最小四件套骨架：先把结构跑通，别急着接真模型
import json, time

# ① 任务集：从文件读，别写死在代码里
with open("YOUR_TASKSET.json", encoding="utf-8") as f:
    tasks = json.load(f)

def llm_client(messages, **kw):
    """可替换的模型入口，别在业务代码里绑死某家 SDK"""
    raise NotImplementedError("接上你自己的模型：YOUR_LLM_ENDPOINT")

def send_email(to, subject, body):
    """不可逆操作，一律 mock，默认不真发"""
    return {"ok": True, "to": to, "subject": subject, "mode": "mock"}

def run_one(task):
    trace = {"task_id": task["id"], "steps": [], "t0": time.time()}
    messages = [{"role": "user", "content": task["input"]}]
    out = llm_client(messages)        # → YOUR_LLM_ENDPOINT
    trace["final_text"] = out
    send_email(task["input"], "", "")  # mock，不真发
    trace["email_sent_to"] = task["expected"]["to"]
    trace["elapsed"] = time.time() - trace["t0"]
    return trace

# ② 成功判定：可执行的，不能是"看着还行"
def is_success(task, trace):
    return all([
        trace.get("email_sent_to") == task["expected"]["to"],
        all(k in trace.get("final_text", "")
            for k in task["expected"]["must_mention"]),
    ])

# ③④ 指标 + 环境快照
rows = []
for t in tasks:
    tr = run_one(t)
    rows.append({"id": t["id"],
                 "ok": is_success(t, tr),
                 "sec": round(tr["elapsed"], 2)})

run_meta = {
    "model": "YOUR_MODEL_NAME",
    "model_version": "YOUR_MODEL_VERSION",
    "temperature": 0.0,
    "doc_snapshot_hash": "YOUR_SNAPSHOT_HASH",
    "ran_at": time.strftime("%Y-%m-%d %H:%M:%S"),
    "tools_mocked": ["send_email"],
}
print(json.dumps({"rows": rows, "run_meta": run_meta},
                 ensure_ascii=False, indent=2))
```

代码本身不重要，重要的是这四件事：题从哪来、怎么算对、跑了多久、当时用什么跑的。

**没有 run_meta 的结果表，过两周就是一堆废纸。**

## 精度是按场景买的，不是越贵越好

| 场景 | 样本量下限 | 判定能粗到什么程度 | 值不值得上模型打分 |
|---|---|---|---|
| 选型 | 30–50 道，覆盖主要场景 | 可以粗，但三个方案必须统一 | 值得，你要的是横向排序 |
| 迭代 | 20–30 道常备，外加本次改动相关的几道 | 不能粗，粗了看不出变化 | 规则能判就别上模型 |
| 上线 | 多少都不嫌多，重点是高风险那几道 | 必须精细，且要单独看副作用 | 高风险项上值得 |
| 汇报 | 能讲清来源就行 | 可解释比精确更重要 | 不需要，越简单越好讲 |

这张表想说的事很土：别在选型阶段追求上线级的精度。你连留哪个方案都没定，花两周做一套上线级评测，最后方案砍了，那两周跟着一起没了。

反过来，也别拿选型用的那 30 道题去拍板上线。那 30 道题里很可能一道"发错邮件"的都没有——不是它不会发错，是你压根没出那道题。

还有个我自己踩过的坑：迭代的时候把题集也一起改了。这周改 prompt 时顺手往题集里加了两道新题，下周跑出来涨了 3 个点——其中 2 个点是新题简单，只有 1 个点算这次改动的功劳。题集得跟代码一样上锁，改题集是另一件事，得分开记一笔。

## 第一版那 15 道题怎么挑

节骨眼在选题上。我自己的三条土办法：

**从真实需求里捞，别坐在工位上编。** "把上周销售数据整理一下发给张三"这种话，得是同事真在群里发过的原话。你编出来的需求，语法干净、信息齐全，你的 Agent 一答一个准，测了个寂寞。

**按类型分层，别全是一个样。** 15 道里至少分四堆：只检索不写东西的、检索完要写邮件的、要跨三个来源交叉核对的、带附件和抄送规则的。全堆在一类上，你测到的还是那个类型。

**故意留几道它容易栽的。** 我知道周报助手有两类题必翻车：几个来源数据打架时它爱和稀泥，不给明确结论；收件人写成"相关负责人"这种模糊称呼时，它会自己瞎猜一个人。这两类我各塞了三道进去。

然后 15 道跑第一遍，它错了五道。别急着改 Agent——先看那五道是不是真错。

我第一版里有两道是我自己题出错了：一道里"上周"指的哪七天没写清，另一道期望它引用的那个数据源当时已经下线了。题本身不合格，判它失败纯属冤枉。**修题比修 Agent 便宜，先修题。**

## 一个常见误会：先有完美评测，才有评测

顺序反了。

我见过不少人的计划表长这样：先攒 500 道题，先上一套开源评测框架，先把执行轨迹（Trace，详见 TA 篇）采集打通——然后再开始评。三个月过去，一样都没落地。

真能跑起来的是这个顺序：15 道题 + 一条能自动判的规则 + 一个记环境信息的字典。跑第一遍你就会发现题出得不好、判定写得太松、有三道题根本跑不通。改，再跑。第二版的 15 道题，比凭空设计的 500 道题有用得多。

这事儿烦就烦在，第一版一定很烂。但第一版不烂的东西，通常一直没开始。

---

**一句话结论**：被问"它行不行"的时候，先反问一句"你要拿这个答案做什么决定"——选型、迭代、上线、汇报是四个不同的问题，一个准确率数字答不了四个。

**下一篇要解决的那个麻烦**：好，就算认了要评测。那能不能直接把评 LLM 的那套搬过来？"给模型打分"这事明明已经有成熟做法了。搬不了，而且多出来的麻烦不多不少正好四个——下一篇逐个拆开讲。

**踩坑征集**：你被问"它准确率多少"的时候是怎么答的？糊弄过去了、还是编了个数字然后被追问到崩？评论区讲讲，我收进 F2 翻车合辑。
