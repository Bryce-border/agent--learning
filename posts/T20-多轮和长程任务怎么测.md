# 它到底记不记得你刚才说了什么：多轮和长程任务怎么测

第三轮，用户说"就按刚才那个格式来"。

周报助手的回复是："请问您希望用什么格式？"

截图发到群里的时候，我第一反应是模型记性差。换了个上下文更长的模型，还是这样。后来翻日志才发现，第二轮之后我压根没把历史传进去——`messages` 里每次只有当前这一条。它不是在装傻，它是真没看见。

这事儿烦就烦在：前面 T6 到 T11 那一整套，测的都是"一条输入，一个终态"。而线上真正被投诉的场景，八成发生在第三轮、第五轮、第十二步。

单轮评测全绿、多轮全崩，这两种结果可以同时成立，一点不矛盾。

## 先把两个东西分开：多轮对话和长程任务

它们崩起来长得像，成因不一样，测法也不一样。

**多轮对话（multi-turn conversation）**：轮次是外部驱动的。用户说一句，Agent 回一句，用户再说一句。中间可能换话题、可能纠正你、可能甩一个"那个""刚才那个"过来让你自己接。变量是**对话状态**——记不记得住、会不会重复问、被纠正了听不听。

**长程任务（long-horizon task）**：只有一条用户输入，但 Agent 自己要走十几二十步。查资料、读文档、比对、写稿、发邮件。中间没人插话。变量是**上下文长度和目标稳定性**——会不会走到第八步就忘了最初要干什么，会不会上下文塞满之后把前面查到的结果挤出去。

在评测代码里这两者几乎同构：都是一个循环，跑多轮，最后判终态。所以放一篇讲。

## 单轮评测漏掉的五种崩法

我把线上投诉翻了一遍，归类下来是这五种。你对着自己的 Agent 过一遍，能对上两三个算正常。

**① 失忆。** 第一轮说"看华东区"，第三轮问"那它跟华南比呢"，它回"请问您说的是哪个区域"。判定的时候别抠字面——它不需要把"华东区"三个字原样复述，只要回复指向的是同一个对象，就算记住了。

**② 复读。** 已经确认过的信息又问一遍。"请问您的邮箱是？"——上一轮刚给过。这个比失忆更招人烦，因为它让用户觉得自己在填一张反复重填的表。

**③ 固执。** 用户说"不对，我要的是华南不是华东"，它下一轮还在分析华东。这类失败在评分表上特别隐蔽——它每一句话单拆出来都没错，只是不肯接受修正。

**④ 串台。** 话题切走之后，上一轮的约束还在生效。前面聊的是"给老板的版本，压到 300 字以内"，切到"给客户的版本"之后它还是只写 300 字。反过来也有，切回来的时候把中间那个话题的上下文带了进来。

**⑤ 撑爆。** 这是长程专属。上下文满到装不下，前面的内容被截掉或者被摘要压掉，它开始编——注意，是编，不是老实说不知道。它已经看不见自己查过什么了，于是重新查一遍，或者干脆按常识补一个数上去。

前四种多轮和长程都会有，第五种只有长程会有。

## 会话怎么组织：三个必须写对的细节

先说工程。这块做错，后面所有分数都是假的。

**独立 session，组内共享。** 每组多轮对话开始前生成一个 `session_id`，这一组每一轮都用同一个。别拿"用户 ID"当 session——同一个用户可能同时在跑两组测试，会串。

**组内串行，组间随便并发。** 同一组里必须一轮跑完再发下一轮。你把五轮并发打出去，Agent 收到的顺序是随机的，测出来的东西毫无意义。

**一轮跑完要等它落库。** 最坑的就是这条。你的 Agent 把对话历史存在数据库或者缓存里，写进去和读出来之间有时间差，常见是几百毫秒到两秒。发完请求立刻发下一轮，下一轮读到的历史可能是空的。

然后你会拿到一份非常漂亮、非常误导人的报告：第 2 轮开始成功率暴跌。

我在这条上浪费了整整一个下午。当时我认定是模型的多轮能力不行，还去对比了三家模型，做了一张某家"长上下文更强"的表。后来加了一行 `time.sleep(2)`，三家全部回到 90% 以上。

不是模型的问题。是我没让它读到该读的东西。

所以判定逻辑里加了一条前置检查：每轮开始前先抓一次会话历史，条数对不上就重试这一轮，重试两次还不对，把这条用例标成 `error` 而不是 `fail`。这个区分很要命——`error` 是测试环境的问题，`fail` 是 Agent 的能力问题。混在一起统计，你会把基础设施的锅算到模型头上。

`error` 不计入分子也不计入分母，这规矩 T7 的自查清单里讲过，同一个道理。

## 整组判，不逐轮判

多轮评测最容易做错的一个决定：逐轮打分，然后取平均。

假设一组三轮，第一轮对、第二轮对、第三轮失忆。逐轮算 2/3 = 66.7%，表格上看着"还行，有进步空间"。

用户体感是什么？他提了三次，最后一次被彻底忘掉。这组对话的体验是**失败**的，不是六十六分。

所以规则很简单：**一组对话算一条用例，整组通过才算通过。** 三轮里任何一轮崩了，这条就不过。

这跟 T7 讲的"主指标决定通过与否"是同一件事。多轮这条线的主指标只有一个：多轮完成率（multi-turn completion rate）。别把它拆成"记忆保留率 85% + 复读率 5% + 固执率 3%"再平均——那个平均值不指向任何真实体验。

整组判会丢诊断信息，所以额外记两个字段：

- `first_failure_turn`：从第几轮开始崩的
- `failure_kind`：崩在失忆、复读、固执、串台里的哪一类

这两个字段比总分有用得多。第 2 轮就崩，八成是历史没注入或者落库没等够；第 5 轮才崩，八成是窗口截断或者摘要压缩把关键信息压没了；一轮不崩但用户体感差，回去查复读。

给个数据结构，直接能塞进你的任务集：

```json
{
  "id": "MT-003",
  "tags": ["multi_turn", "memory", "medium"],
  "turns": [
    {
      "turn": 1,
      "input": "把华东区上周的销售数据整理成周报",
      "must_contain": ["华东", "上周"]
    },
    {
      "turn": 2,
      "input": "华南呢，对比一下",
      "must_refer_to": ["华东"],
      "must_contain": ["华南"]
    },
    {
      "turn": 3,
      "input": "就按这个对比的格式，发给张伟",
      "must_refer_to": ["华东", "华南"],
      "must_not_repeat_question": true
    }
  ],
  "max_total_tokens": 12000
}
```

三个自定义字段值得解释。

`must_refer_to` 判的是"还记不记得"，但**不要求原样出现**。判定器要检查回复里的指代能不能落到前面提过的那个对象上，不是字符串匹配。第三轮写"这两个区""它们""对比结果"都算过。

`must_not_repeat_question` 判复读。如果它又问了一遍已经在第一轮给过的信息（发给谁、要多长、什么格式），这条直接不过。

`max_total_tokens` 是给成本上的闸。多轮的成本按组累加，不按轮。这一条不设，一组二十轮的对话能把你的日预算跑光。

## 记忆衰减曲线：比一个平均分有用十倍

固定轮数取平均，你只能得到一个数。换个做法：把对话拉长，在**特定轮次**插入需要引用前文的问题，看保留率怎么掉。

构造不难。一组 8 轮的对话，在第 2、3、5、8 轮各插一个"必须用到第 1 轮信息"的追问。跑二十组，按轮次统计。

跑出来大概是这个形状（下面是示意，数字看你自己的 Agent，重点看斜率）：

| 插入轮次 | 第 2 轮 | 第 3 轮 | 第 5 轮 | 第 8 轮 |
|---|---|---|---|---|
| 记忆保留率 | 100% | 92% | 74% | 41% |

一条缓慢下降然后突然断崖的曲线，和一条平滑下降的曲线，指向完全不同的修法。

断崖通常意味着撞上了某个硬边界：窗口截断的位置、摘要压缩的阈值，或者你代码里那个 `history[-6:]` 的切法。平滑下降才是真正的"记性随距离衰减"，那种得考虑加显式记忆——把关键实体抽出来单独存，别指望它一直待在上下文里。

我第一版曲线是断崖的，第 6 轮从 88% 掉到 30%。查了半天模型，最后发现是我自己写的滑动窗口取最近 5 轮。到第 6 轮，第 1 轮的信息刚好被挤出去。

说白了，那不是模型忘了，是我让它忘的。

## 长程任务：多盯两件事

长程任务的评测框架跟多轮一样——一条用例、一个循环、一个终态——但要多盯两件事。

**第一件：目标漂移。**

跑到第十二步，它还在干活，但干的已经不是最初那件事了。举例：让它"整理上周三个渠道的销售数据，写一份 800 字周报，发给张伟"。它查了数据、写了稿、也发了邮件，收件人没错，写的是本周数据——因为中途它调了一个"最近七天"的接口。

这种失败在只看终态的评测里会被判通过：邮件发了、收件人对、字数够。内容错了，但你的判定器没查内容。

做法：把最初的任务约束在终态再验一遍，而且要用**独立于 Agent 自我陈述**的证据去验。别问它"你写的是上周的数据吗"，去 mock 信箱里读那封邮件正文里的日期范围。T4 讲的"说没做不等于没做"，在这里反过来用：说做了也不等于做对了。

**第二件：中间里程碑。**

一条长任务里，有些步骤是必须发生的。查了三个渠道、做了一次汇率换算、发信前校验了收件人。这些不发生的后果，有时终态看不出来（它可能猜对了），但过程已经烂了。

做法：给每条长任务标 2 到 4 个 `required_steps`，从 Trace 里核对有没有真的发生。注意别标太多——标十个等于要求它照着你的剧本演，换个更优的路径就被判失败，那是把评测做成了路径复刻。

这里有个反直觉的点，T3 那篇提过一遍：公开 Benchmark 没有一个靠"匹配动作轨迹"判成败，全都查终态。为什么？因为路径可以有很多条，最优解不唯一。所以 `required_steps` 只能标业务上**不可跳过**的步骤，不能标"我希望它这么走"的步骤。

## 一段能跑的判定

不贴完整框架，只给判定那一段。跑对话的部分跟 T8 的主循环一样，把 `run_once` 换成 `run_conversation` 就行。

```python
def judge_conversation(turns_result, spec, trace):
    """一组多轮对话的判定：整组通过才算通过。"""
    failures = []

    for i, (turn_spec, turn_out) in enumerate(zip(spec["turns"], turns_result), start=1):
        text = turn_out["text"]

        for kw in turn_spec.get("must_contain", []):
            if kw not in text:
                failures.append((i, "missing_keyword", kw))

        # 复读检查：把上一轮已经给过的信息又问一遍
        if turn_spec.get("must_not_repeat_question"):
            asked = extract_questions(text)          # 返回本次回复里提出的问题
            if any(a in q for q in asked for a in turn_out["already_answered"]):
                failures.append((i, "repeat_question", None))

        # 记忆检查：指代能不能落到前面提过的实体上
        for ref in turn_spec.get("must_refer_to", []):
            if not resolve_reference(text, ref, turns_result[:i - 1]):
                failures.append((i, "lost_context", ref))

    # 长任务里程碑：从 trace 里核对，不看 Agent 自己怎么说
    called = {s["tool"] for s in trace["tool_calls"] if s["ok"]}
    for step in spec.get("required_steps", []):
        if step not in called:
            failures.append((None, "missing_step", step))

    total_tokens = sum(t["tokens"] for t in turns_result)
    if total_tokens > spec.get("max_total_tokens", 10**9):
        failures.append((None, "budget_exceeded", total_tokens))

    return {
        "passed": not failures,
        "first_failure_turn": next((f[0] for f in failures if f[0]), None),
        "failure_kind": failures[0][1] if failures else None,
        "failures": failures,
        "total_tokens": total_tokens,
    }
```

`resolve_reference` 是这块唯一需要模型的地方——判断"这两个区"指的是不是前面那两个区，规则判不了。但它是个**二分类**，prompt 很短，成本比让裁判通读整段对话低一个量级。

顺便提醒一句：别一上来就给整组对话上个 Judge，打个 1 到 5 分。分数你没法用，而且第三轮崩了它可能还给你 3 分。先把规则能判的（关键词、复读、里程碑、预算）判掉，剩下"指代解没解对"这一小块才交给模型——这就是 T16 那个三层路由，只是换了个场景。

## 成本：按组估，别按轮估

最后说钱。多轮评测的成本估算，是很多人栽的地方。

一组 5 轮的对话，不是"1 次任务"的钱。第 5 轮要把前 4 轮的历史一起送进去，所以 token 消耗是累加且递增的：第 1 轮 1 份，第 5 轮可能是 4 份。一组的实际输入 token 大概是单轮的 8 到 12 倍，具体看你的历史保留策略。

预算这么估：`组数 × 单轮均价 × 轮数 × 0.6`，0.6 是个经验系数，因为前面几轮短。按"30 条用例"估会低估到离谱。

还有个省钱的做法：多轮评测不用全量跑。挑 10 到 15 组覆盖不同对话形态——追问型、纠正型、切换型、长链型——比跑 100 组同质的追问有用。多轮的失败是**形态**问题，不是数量问题。

## 最后

一句话结论：单轮评测回答"它答得对不对"，多轮和长程评测回答"它靠不靠得住"——而后者才是投诉的来源。

下一篇要解决的麻烦很具体：上面那个 `required_steps` 是从 Trace 的工具调用记录里核对的，但"调了这个工具"和"调对了这个工具"是两回事。选错工具、参数传错、失败了重试三次还在原地打转——这些怎么单独测，下一篇讲工具调用评测。

你在多轮上踩过什么坑？我特别想收那种"以为是模型不行，最后发现是自己代码问题"的例子——上面那个 `sleep(2)` 只是我踩的其中一个。评论区报一下，攒够了我单独开一篇错题本。
