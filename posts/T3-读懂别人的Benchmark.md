# 读懂别人的 Benchmark：五个基准各在测什么

466 道题。人类答对 92%，同一批题上配备插件的 GPT-4 平均只有 15%。

这两个数字出自 GAIA 的论文（arXiv:2311.12983，2023 年 11 月）。我第一次看见时不信，去翻了原文，是真的。那时候我手上有 20 道自己攒的题，正准备拿来给周报助手打分。看完这五个基准测试（Benchmark，详见 TA 篇）的题，那 20 道我全删了。

## 为什么得先看别人的题

自己攒题最大的问题，不是题少，是你从没见过"被设计过的题"长什么样。

我那 20 道题是这么来的：打开周报助手，随手敲几条它平时会收到的需求，把输出看一眼，觉得还行的就记成"成功案例"。攒到 20 道，自我感觉相当好。

问题在哪？这 20 道题里有 14 道是单轮问答——一句话进去，一段话出来，中间不需要任何步骤。剩下的 6 道要搜点东西，但搜一次就够。整套题里没有一道需要跨三个来源交叉验证，没有一道的答案是"把附件发给特定的人"，没有一道它有可能失败两次。

**说白了，我攒的不是题，是它已经会做的那部分。**

而设计过的题恰恰相反：出题的人先想清楚"这个能力在什么时候会露馅"，再倒着把题造出来。看别人怎么造题，比看别人的分数有用一百倍。

下面五个，逐个用同一套四问拆：任务形态是什么 / 跑在什么环境里 / 怎么判成功 / 适合谁拿来用。

## GAIA：把答案设计成不需要裁判的东西

- **提出方与时间**：Meta FAIR、HuggingFace、AutoGPT、GenAI Meta（作者包括 Grégoire Mialon、Clémentine Fourrier、Yann LeCun 等），arXiv:2311.12983，2023 年 11 月
- **任务形态**：真实世界的开放式问答。要网页浏览、要工具组合、要处理附件（有的题带图片、表格、音频），本质上是"你能不能自己找到路"
- **规模**：466 道题，公开其中 300 道的答案用于排行榜
- **难度分级**：三个 Level。Level 1 一次外部查询就够；Level 2 要多步查找加格式转换；Level 3 要跨多个来源交叉验证
- **怎么判成功**：答案被设计成事实型的、无歧义的字符串、数字或列表，**精确匹配（Exact Match，详见 TA 篇）**就行，不需要裁判模型
- **论文里的关键数字**：人类 92%，配备插件的 GPT-4 平均 15%（Level 1 约 30%，Level 3 接近 0）——这是 GAIA 论文在 2023 年 11 月用那个脚手架跑出来的，不是今天的数字

**这一手最值钱的地方**：它用"把答案设计成无歧义"换掉了"必须靠 LLM-as-a-Judge（详见 TA 篇）打分"这个大麻烦。代价是它只看最终答案，**不看推理过程**。蒙对的题也算对。

对周报助手的直接启发：Level 2 和 Level 3 那两档，正好对应"查三个来源交叉验证，再写成一封信"。我原来的 20 道题，全在 Level 1 以下。

## AgentBench：一个环境看不出泛化

- **提出方与时间**：清华大学 KEG 实验室（刘潇等），与俄亥俄州立大学、UC Berkeley 合作；arXiv:2308.03688，2023 年 8 月，ICLR 2024 Poster，2025 年 10 月还有 v3 版预印本更新
- **任务形态**：八个互不相干的交互环境——操作系统（bash）、数据库（SQL）、知识图谱、数字卡牌对战、侧向思维谜题、家务（ALFWorld）、网络购物（WebShop）、网页浏览（Mind2Web）
- **规模**：约 1,360 条测试样本
- **环境**：分成 code-grounded / game-grounded / web-grounded 三大类，其中 5 个自建、3 个改造自已有数据集，全部跑在 Docker 里
- **怎么判成功**：程序化判定，算成功率（SR），要求最终答案或环境状态与预期完全一致
- **论文结论**：顶级商用模型明显强于当时的开源模型；作者直接把"长期的推理、决策和指令跟随能力不足"点成可用 Agent 的主要障碍
- **开源**：github.com/THUDM/AgentBench，Apache 2.0

别只看总分，要看它在八个环境上的分项。一个 Agent 在 SQL 环境里八十分、在网页浏览里二十分，那不是个"八十分的 Agent"，那是个只会写 SQL 的 Agent。

**对新手的启发**：单个环境只会奖励特化能力，横跨多个环境才看得出是不是真泛化。你给自己 Agent 出的题，如果全在一个环境里，你测到的其实是那个环境。

## WebArena：判定写在环境状态上

- **提出方与时间**：卡内基梅隆大学（Shuyan Zhou、Frank F. Xu、Hao Zhu 等，Graham Neubig 组）；arXiv:2307.13854，2023 年，ICLR 2024
- **任务形态**：四个自建的、完全可用可复现的真实 Web 应用——电商站 OneStopShop、论坛 Postmill、GitLab、类 Wikipedia 的 CMS（MediaWiki），外加计算器、地图、笔记等辅助站点
- **规模**：812 条自然语言任务
- **观测空间**：可选的 URL 加页面内容（截图 / DOM 树 / 无障碍树）
- **怎么判成功**：每道题自带一个可程序化校验的成功函数，直接去查数据库或页面最终状态；成功路径里没有 LLM Judge
- **论文里的关键数字**：GPT-4 加 ReAct 脚手架 14.41%，人类基线 78.24%——同样是 2023 年那篇论文报的

这是这个系列里我最想让读者抄走的一招：**判定写在环境状态上，不写在答案文本上**。

它问的从来不是"你说你下单了吗"，而是"订单表里现在有没有这一条"。这个思路搬到周报助手身上，就是别问"邮件写好了吗"，去查那个假邮箱里现在躺着几封信。

它也有个坦诚的取舍：如果 Agent 一路乱点，最后阴差阳错把状态改对了，也算成功。作者认了这件事。

## τ-bench：一次成功不算本事

- **提出方与时间**：Sierra（Shunyu Yao、Noah Shinn、Pedram Razavi、Karthik Narasimhan）；arXiv:2406.12045，2024 年 6 月 17 日，ICLR 2025 Poster
- **任务形态**：多轮对话。由 LLM 扮演用户（带意图、人设、耐心），被测 Agent 通过领域 API 读写数据库，并且要在整段对话里遵守一份成文的业务规则
- **领域与规模**：retail（退换货、订单）与 airline（取消、改签、行李），共 165 道题（retail 115，airline 50）
- **怎么判成功**：比对任务结束后的数据库状态是否与预期一致，另外还有一个独立的规则遵守（policy compliance）判定
- **标志性指标**：**pass^k**（详见 TA 篇）——同一个任务独立跑 k 次**全部**成功的比例，衡量的是稳定性，不是"碰运气的 best-of-k"
- **论文里的关键数字**：当时最强的 function calling 模型（比如 gpt-4o）成功率不足 50%，retail 域的 pass^8 低于 25%
- **后续**：官方排行榜把 user simulator 固定为 GPT-4o；后续还有 τ²-bench、τ³-bench
- **开源**：github.com/sierra-research/tau-bench，MIT

低于 25% 的 pass^8 是什么概念？同一个退换货任务，让它独立跑八次，八次全做对的概率不到四分之一。它明明能成功，只是不稳定。

这条最贴近周报助手：终态是"那封信现在躺在谁的邮箱里"，中间还要遵守"抄送谁、不抄送谁、附件必须带上"这类成文规矩。

顺便提醒一句：pass^k 和常见的 pass@k 是两回事，别看混了。前者要求 k 次全对，后者只要 k 次里对一次。

## SWE-bench：以及它已经退役的那个子集

- **提出方与时间**：普林斯顿大学（Carlos E. Jimenez、John Yang 等），2024 年，ICLR 2024 Oral
- **任务形态**：给一个真实的 GitHub issue，加上出问题时的代码仓库快照，Agent 要自己定位、改代码、产出 patch
- **规模**：全集 2,294 条任务，来自 12 个流行 Python 开源项目（Django、Flask、scikit-learn、sympy、matplotlib、requests 等）
- **Verified 子集**：2024 年 8 月 13 日，OpenAI Preparedness 团队与普林斯顿团队合作发布，是 500 道经真人开发者逐题确认可解的题
- **怎么判成功**：跑单元测试。FAIL_TO_PASS（原本失败的测试现在要通过）加 PASS_TO_PASS（原本通过的不能被改坏）。全过才算 resolved，**不给部分分**
- **论文里的关键数字**：Verified 发布时，GPT-4o 加 Agentless 脚手架是 33.2%

这里必须先错后对一下。我第一次看到 33.2% 这个数，以为它代表当前的水平线。不是。那是 2024 年 8 月 Verified 发布当时、用 GPT-4o 配 Agentless 那个特定脚手架跑出来的初始数字。

然后是一条时效性提醒，也是这篇里我最想让读者记住的一条：**OpenAI 已于 2026 年 2 月 23 日宣布不再把 SWE-bench Verified 用于前沿模型评测**，理由有两个——测试本身存在缺陷，以及训练数据污染。社区普遍认为这个子集已经接近饱和，转而使用 SWE-bench Pro、SWE-Lancer 等后继基准。

（这事儿还有一个让人不太舒服的副作用：你今天在中文技术博客里看到的 SWE-bench Verified 分数，有一大半没写年份和脚手架，直接拿来对比，等于拿三个不同年份的东西排一张表。）

去污染（Decontamination，详见 TA 篇）这个话题我们留到 T5 专门讲，SWE-bench Verified 就是那个最鲜活的真实案例——一个曾经公认好用的评测集，会因为被考烂了而失效。

## 一张横向速查表

| Benchmark | 场景 | 题量 | 判定落在哪 | 要工具吗 | 要 Judge 模型吗 | 主要失效模式 |
|---|---|---|---|---|---|---|
| GAIA | 开放网络问答 | 466 | 最终答案精确匹配 | 要 | 不需要 | 只看终态，蒙对也算对 |
| AgentBench | 8 个交互环境 | 约 1,360 | 环境状态 / 答案比对 | 要 | 不需要 | 单环境高分可能是特化 |
| WebArena | 自建 Web 应用操作 | 812 | 数据库与页面状态（成功函数） | 要 | 不需要 | 误打误撞也算成功 |
| τ-bench | 客服多轮对话 | 165 | 数据库状态 + 规则遵守 | 要 | 不需要（但用户模拟用 LLM） | 能成功但不稳定 |
| SWE-bench | 真实 issue 修 bug | 2,294（Verified 500） | 单元测试 FAIL_TO_PASS / PASS_TO_PASS | 要 | 不需要 | 已被考烂，污染严重 |

## 它们共同的套路

拆完五个，有两件事它们是商量好的一样。

**第一件，全部把判定做成了客观的、程序化的、不依赖模型主观打分的事。** 哪怕任务是开放式的（GAIA 的问答很开放），它们也宁可先把答案设计成无歧义的短串，或者把判定挪到环境状态上去，也不肯请一个模型来当裁判。开放式输出确实是得上裁判的（那是 T12 之后的事），但那是被逼到最后一步才走的路。

**第二件，五个里没有一个靠匹配动作轨迹来判成败，全都看终态。** 这一点最反直觉，因为它跟我们从小熟悉的"按步骤给分"完全相反。你做对了就行，至于你是怎么做到、中间绕了哪些路、有没有照标准解法走，它不管。

## 新手最容易犯的错

**拿排行榜上的分数当自己 Agent 的能力证明。** 这是头号错误。别人的分数是别人在那个 benchmark 的题上、用那个脚手架、在那个时间点跑出来的。你的 Agent 跑的是你的业务，两件事之间隔着一整个现实。

其次是**不看脚手架直接比数字**。14.41% 是 GPT-4 加 ReAct 跑的，换个脚手架可能就是另一个数。引用任何分数都必须同时写明"谁在什么时候用什么脚手架跑出来的"，否则不可比——这句话值得抄在笔记上。

第三个错误是**把别人的题直接搬来当自己的测试集**。公开数据集顶多是个素材，怎么改成自己的题是 T5 的活。

还有一条最阴：**不查时效性**。你现在看到的这个 benchmark，可能已经像 SWE-bench Verified 一样退役了。

## 带走这个模板

以后再遇到任何一个新 benchmark，拿这四问套一遍就行：

```text
Benchmark 拆解模板（复制到你的笔记里）

1. 任务形态：单轮还是多轮？要不要工具？一道题大概要走几步？
   → 我手上这批题，最复杂的那道要走几步？

2. 执行环境：跑在真实互联网上，还是自建沙箱里？能复现吗？
   → 我自己的题，外部依赖有几个？它们一个月变几次？

3. 怎么判成功：判定落在答案文本、环境状态，还是动作序列上？
   → 我的判定现在落在哪？有没有可能搬到状态上去？

4. 适合谁用：它的题跟我的场景重叠多少？
   → 我能不能直接抄它的判定方式，而不抄它的题？

附：引用它家分数时，必须同时记下
   - 谁跑的（哪个模型 + 哪个版本）
   - 什么时间跑的（论文见刊时间 or 榜单更新时间）
   - 用什么脚手架跑的
   - 这个 benchmark 现在还有没有在维护
```

四个空填完，你对这个 benchmark 的理解就超过九成只看过排行榜的人了。

---

**一句话结论**：这五个 benchmark 最值钱的不是分数，是它们处理"怎么判成功"的两招——把答案设计成无歧义的，或者把判定搬到环境状态上去——而它们全都不看过程、只看终态。

**下一篇要解决的那个麻烦**：终态这套思路有个大前提——答案得是唯一确定的。可周报助手写的是一封邮件，它没有"标准答案"可以比对。下一篇讲那个认知拐点：答案对了，不等于事办成了。

**踩坑征集**：你有没有把某个公开榜单的分数直接写进过汇报材料，被人追问一句"这是谁跑的"就卡住了？或者你照着某个 benchmark 攒过题，攒完发现根本测不出东西？评论区说说，我挑几个典型的进 T5。
