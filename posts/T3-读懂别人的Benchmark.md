# Benchmark 怎么读：五个基准的判定都落在哪

先说结论：GAIA、AgentBench、WebArena、τ-bench、SWE-bench 这五个，**没有一个请模型当裁判**。它们全部把"算不算成功"做成了程序能跑的事——要么把答案设计成无歧义字符串，要么直接查环境状态，要么跑单元测试。

这一条决定了它们的题能不能抄、分能不能比。这篇把概念、五个基准的判定设计、以及怎么把它们拆成自己能用的东西，一次讲清。

## 一、先把四个词分清

这四个词天天混着用，混了就读不懂 benchmark 的文档。

| 词 | 是什么 | 例子 |
|---|---|---|
| Benchmark（基准测试） | 一整套**评测方案**：题 + 环境 + 判定 + 计分规则 | SWE-bench 是 benchmark |
| Dataset（数据集） | 只是那批题，不带环境和判定 | SWE-bench 里的 2,294 条 issue 是 dataset |
| Test Case（测试用例） | 数据集里的一条，通常含输入与期望 | 某一条 issue + 对应的测试 |
| Ground Truth（标准答案） | 这一条的正确答案或正确终态 | 修复后应通过的单元测试集合 |

最容易搞错的是第一个和第二个：**dataset 是素材，benchmark 是方案**。你拿别人的 dataset 来用，判定还是得自己写；抄 benchmark 才连判定一起抄。

## 二、五个基准，一张总表

| Benchmark | 谁做的 / 什么时候 | 题目形态 | 题量 | 判定落在哪 |
|---|---|---|---|---|
| GAIA | Meta FAIR 等，arXiv:2311.12983，2023-11 | 真实世界开放问答，要浏览、要工具、带附件 | 466 | 最终答案精确匹配 |
| AgentBench | 清华 KEG 等，arXiv:2308.03688，ICLR 2024 | 8 个交互环境（bash / SQL / 网页 / 卡牌…） | 约 1,360 | 环境状态或答案比对 |
| WebArena | CMU，arXiv:2307.13854，ICLR 2024 | 自建的真实 Web 应用操作 | 812 | 数据库与页面状态（成功函数） |
| τ-bench | Sierra，arXiv:2406.12045，ICLR 2025 | 客服多轮对话，LLM 扮用户，遵守成文规则 | 165 | 数据库状态 + 规则遵守 |
| SWE-bench | 普林斯顿，ICLR 2024 | 真实 GitHub issue，自己改代码出 patch | 2,294（Verified 500） | 单元测试全过 |

记数字没意义，记它们的**判定设计**才有用。

拿到任何一个陌生 benchmark，先做三个快检，两分钟能做完：

1. **判定落在哪**——答案文本、环境状态、还是动作序列？落在文本上的，分数最容易被措辞影响。
2. **难度有没有梯度**——像 GAIA 分三个 Level 那样，还是全都一个难度？没有梯度的题测不出能力边界。
3. **最近一次更新是什么时候**——看 repo 最后一次提交、榜单有没有新条目。一年没动的，多半已经饱和或被污染。

三个都过，再花时间读题；过不了，直接换一个。

逐个看。

## 三、逐个看判定

**GAIA：把答案设计成不需要裁判的东西。**

三个难度档：Level 1 一次查询够，Level 2 多步查找加格式转换，Level 3 跨来源交叉验证。论文报的数字是人类 92%、配插件的 GPT-4 平均 15%（Level 3 接近 0）——**2023 年 11 月、那套脚手架跑出来的**，不是今天的水平。

它最值钱的一手是用"答案无歧义"换掉了"必须上裁判打分"，代价是只看终态，蒙对也算对。

**AgentBench：一个环境看不出泛化。**

8 个环境分三类（代码、游戏、网页），5 个自建、3 个改造自现有数据集，全跑在 Docker 里。看它别只看总分：SQL 环境 80 分、网页环境 20 分，那不是"80 分的 Agent"，那是只会写 SQL 的 Agent。

**WebArena：判定写在环境状态上。**

四个自建站点（电商、论坛、GitLab、类 Wikipedia），812 条任务。每道题自带一个可程序化校验的成功函数，直接查数据库或页面最终状态，全程没有 LLM Judge。论文里 GPT-4 + ReAct 是 14.41%，人类 78.24%。

**这一招最值得抄**：别问"你说你下单了吗"，去查订单表里有没有这条。它也有个坦诚的取舍——一路乱点最后把状态改对了，也算成功。

**τ-bench：一次成功不算本事。**

retail 115 题、airline 50 题，共 165。判定是任务结束后的数据库状态 + 规则遵守。标志性指标是 **pass^k**：同一任务独立跑 k 次**全部**成功。当时最强的 function calling 模型成功率不足 50%，retail 的 pass^8 低于 25%。

所以低于 25% 不代表"不会做"，代表"能做对但不稳定"。这条最像真实业务。

**SWE-bench：以及它退役的那个子集。**

2,294 条真实 issue，判定跑单元测试：FAIL_TO_PASS（原本失败的现在通过）+ PASS_TO_PASS（原本通过的不许改坏），全过才算 resolved，不给部分分。Verified 子集是 2024-08-13 与 OpenAI 合作发布的 500 道经人工确认可解的题，发布时 GPT-4o + Agentless 是 33.2%。

**时效性提示，这篇最该记的一条**：OpenAI 已于 **2026 年 2 月 23 日**宣布不再把 SWE-bench Verified 用于前沿模型评测，理由是测试本身有缺陷 + 训练数据污染。社区转向 SWE-bench Pro、SWE-Lancer 等后继基准。

## 四、它们共同的套路

**第一，判定全部程序化。** 哪怕任务是开放式的，也宁可先把答案设计成短串、或把判定挪到环境状态上，也不肯请模型当裁判。开放式输出确实得上裁判——但那是被逼到最后一步才走的路（T12 才讲）。

**第二，没有一个靠匹配动作轨迹判成败。** 这条最反直觉，因为它跟"按步骤给分"完全相反：你做对了就行，中间绕没绕路、是不是标准解法，它们不管。

理解这两条，你就明白为什么自己攒的题总测不出东西——大概率是判定写在了"看起来像不像"上。

## 五、怎么用：抄判定，不抄题

三步，按顺序做：

**第一步，找它的判定写在哪。** 答案文本、环境状态、还是动作序列？三者里，状态最稳，文本最脆，动作序列最不该用。

**第二步，把这个判定方式搬到自己的任务上。** 比如你的 Agent 会发邮件，判定就别看它写的正文，去看假邮箱里躺着几封、收件人字段是什么。

**第三步，只借题型，不借原题。** 公开题大概率已经被模型背过，而且跟你的业务不重叠。借它"Level 3 那种要跨三个来源"的结构，自己出三道。

判定有且只有三种落点，选错落点，后面全白费：

| 落在哪 | 稳不稳 | 写起来贵不贵 | 什么时候用 |
|---|---|---|---|
| 答案文本 | 脆（措辞一变就判错） | 便宜 | 答案是唯一短串时（GAIA 这类） |
| 环境状态 | 稳（查数据库/信箱即可） | 中等 | Agent 会改外部世界时，优先这个 |
| 动作序列 | 最脆（换个更优路径就冤枉） | 中等 | 只在业务上不可跳过的步骤上用 |

一句话：**能查状态就别比文本，能判终态就别比路径。**

### 引用任何分数，都要带三元组

看到"某模型 85%"这种话，先问：**谁跑的、什么时候跑的、用什么脚手架跑的**。

14.41% 是 GPT-4 加 ReAct 跑出来的，换个脚手架就是另一个数；33.2% 是 2024 年 8 月 Verified 刚发布时的初始值。中文博客里一大半 SWE-bench Verified 分数既没年份也没脚手架，直接横着比，等于拿三个不同年份的东西排一张表。

记不住就记一句话：**没有三元组的分数，不能进汇报材料。**

## 最后

这五个基准最值钱的不是分数，是它们处理"怎么算成功"的两招：把答案设计成无歧义的，或者把判定搬到环境状态上。

下一篇换个方向：终态判定有个前提——答案得唯一确定。可周报助手写的是一封邮件，没有标准答案可比对。那时你要判的就不止"对不对"，还有"做没做"和"有没有做过头"。
