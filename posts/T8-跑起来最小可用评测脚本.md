# 跑起来：第一版脚本要丑，但要能跑

30 道题，跑一次 4 分钟。

我第一次看到这个数字以为是脚本写错了，翻完日志才发现：4 分钟里有 3 分 40 秒卡在同一个任务上，它在等一个永远不返回的内部文档接口，而我的脚本老老实实地陪它等到天荒地老。

这就是没有超时处理的评测脚本——它不会报错，不会崩溃，它就那么安静地卡着，让你以为评测很慢。

上一篇我们把指标挑好了（详见 T7），这一篇把它变成能跑的东西。目标很具体：一个 Python 文件，纯标准库，加载 JSONL 任务集 → 跑 Agent → 调判定器 → 吐一张 CSV。中间不引入任何评测框架，不装任何 pip 包。

先说清楚一件事：这份脚本你大概两周后就会扔掉。它存在的价值就一个——让你在两天之内拿到第一张结果表。设计一个能用到明年的架构是 P1–P4 的事，现在别想。

## 先定死数据结构：一行 JSONL 加一张结果表

任务集用 JSONL，一行一个任务，好处是能直接 `wc -l` 数条数，也能用文本 diff 看改动。

```json
{"id":"wr-001","query":"整理上周销售数据，发邮件给张总","tags":{"type":"email","difficulty":"medium","risk":"high"},"success_criteria":{"must_contain":["销售额","环比"],"must_call_tool":["search_internal","send_email"],"email_to":["zhang@example.com"],"max_len":500}}
```

```json
{"id":"wr-002","query":"查一下竞品上周有没有发新版，写进周报","tags":{"type":"search","difficulty":"easy","risk":"low"},"success_criteria":{"must_contain":["竞品"],"must_call_tool":["search_web"],"max_len":500}}
```

`success_criteria` 是 T6 那篇的产物，这里直接用。字段解释一句：`must_contain` 判结果内容，`must_call_tool` 判过程，`email_to` 和 `max_len` 判约束——这三层对应 T4 讲的结果 / 过程 / 副作用。顺带一提，`judge()` 里那句"查 mock 信箱，不看 Agent 自己怎么说"也是同一个道理：Agent 说自己发了邮件，不等于真的发了（详见 T24）。

有副作用的工具全部 mock，这是硬规矩：

```python
# 邮件永不真发，只往内存信箱里记一笔，判定器查这个
SENT_MAILBOX = []

def mock_send_email(to, subject, body):
    SENT_MAILBOX.append({"to": to, "subject": subject, "body": body})
    return {"ok": True, "mock": True, "message_id": f"mock-{len(SENT_MAILBOX)}"}
```

删数据、下单、改权限同理，一个都不许真跑。你的评测脚本不该拥有破坏生产环境的能力。

结果表定 11 列，字段名跟 T7 那份指标字典完全对得上：

```python
RECORD_FIELDS = ["id", "type", "difficulty", "success", "reason", "duration_s",
                 "prompt_tokens", "completion_tokens", "cost_usd",
                 "steps", "tools_called"]
```

`reason` 这一列最容易被省略，也最容易被追悔。先记住，下面还会讲。

任务集要多少条？我的建议是 30 条起步，别对着 5 道题反复调。5 道题的时候，一道题的成功与否就是 20 个百分点，你会为了这 20 个点去改 prompt，改完发现其实是那道题本身有歧义。30 条的话一道题只占 3.3 个点，才谈得上看趋势。标签怎么打、难度怎么分级是 T5 的事，这里只要保证 `tags` 里有 `type` 和 `difficulty` 两个字段就行，汇总函数要靠它们分组。

## 主循环：超时、并发、记录，三件事一个都不能少

`run_agent` 返回的那个 `trace`，就是 **Agent Trace（执行轨迹）**（详见 TA 篇）的极简版：一次运行里的模型调用、工具调用和最终结果，先记下来再说。现在只留四个字段，够用就行。

```python
# eval_min.py —— 最小可用评测脚本，纯标准库
import csv, json, math, time
from concurrent.futures import ThreadPoolExecutor, as_completed
from concurrent.futures import TimeoutError as FuturesTimeout

TIMEOUT_S = 60      # 单任务硬超时
MAX_WORKERS = 4     # 并发上限，先小一点，别一上来把限流打满
PRICE_IN = 0.000002   # 每千 input token 单价，换成 YOUR_PRICE_IN
PRICE_OUT = 0.000008  # 每千 output token 单价，换成 YOUR_PRICE_OUT


# ---------- 1) 可替换的模型调用：只改这里，别动后面 ----------
def llm_client(messages, temperature=0.0, **kwargs):
    """返回 {"content": str, "usage": {"prompt_tokens": int, "completion_tokens": int}}
    替换点：YOUR_LLM_ENDPOINT / YOUR_API_KEY / 你自己的 SDK"""
    raise NotImplementedError("在这里接 YOUR_LLM_ENDPOINT")


# ---------- 2) 可替换的 Agent：输入 testcase，输出 trace ----------
def run_agent(case, llm=llm_client):
    """真实 Agent 写在这里：循环调 llm、调工具，最后收口成一个 trace dict。
    下面这段是 mock，用来验证脚本本身跑得通——换成你自己的多步循环即可。"""
    resp = llm([{"role": "user", "content": case["query"]}], temperature=0.0)
    return {
        "answer": resp["content"],
        "tool_calls": ["search_internal", "send_email"],  # 从你的 trace 里抽，这里是占位
        "usage": resp["usage"],
        "steps": 4,
    }


# ---------- 3) 超时包装：没有它，一个卡死的任务拖垮整次评测 ----------
def run_with_timeout(fn, args=(), timeout_s=TIMEOUT_S):
    ex = ThreadPoolExecutor(max_workers=1)
    fut = ex.submit(fn, *args)
    try:
        return fut.result(timeout=timeout_s)
    except FuturesTimeout:
        return {"timeout": True, "timeout_s": timeout_s}
    finally:
        # 关键：不能等卡死的线程，否则这里会一直阻塞，超时就白设了
        ex.shutdown(wait=False)


# ---------- 4) 判定器：规则层，判不了的留给后面的模型裁判 ----------
def judge(case, trace):
    """返回 (success: bool, reason: str)。reason 为空串表示成功。"""
    if trace.get("timeout"):
        return False, f"timeout after {trace['timeout_s']}s"

    c = case["success_criteria"]
    ans = trace.get("answer", "") or ""
    called = set(trace.get("tool_calls", []))

    for kw in c.get("must_contain", []):
        if kw not in ans:
            return False, f"缺少关键内容: {kw}"
    for tool in c.get("must_call_tool", []):
        if tool not in called:
            return False, f"未调用工具: {tool}"
    if "max_len" in c and len(ans) > c["max_len"]:
        return False, f"字数超限 {len(ans)} > {c['max_len']}"
    if "email_to" in c:
        sent = {m["to"] for m in SENT_MAILBOX}   # 查 mock 信箱，不看 Agent 自己怎么说
        if not set(c["email_to"]).issubset(sent):
            return False, f"收件人缺失: 期望 {c['email_to']}，实际 {sorted(sent)}"
    return True, ""


# ---------- 5) 单条执行 ----------
def run_one(case):
    SENT_MAILBOX.clear()          # 每个任务独立信箱，别串味
    t0 = time.time()
    trace = run_with_timeout(run_agent, (case,), TIMEOUT_S)
    duration = round(time.time() - t0, 1)
    ok, reason = judge(case, trace)

    u = (trace.get("usage") or {})
    p_tok = u.get("prompt_tokens", 0)
    c_tok = u.get("completion_tokens", 0)
    return {
        "id": case["id"],
        "type": case["tags"].get("type", ""),
        "difficulty": case["tags"].get("difficulty", ""),
        "success": ok,
        "reason": reason,
        "duration_s": duration,
        "prompt_tokens": p_tok,
        "completion_tokens": c_tok,
        "cost_usd": round((p_tok * PRICE_IN + c_tok * PRICE_OUT) / 1000, 6),
        "steps": trace.get("steps", 0),
        "tools_called": "|".join(trace.get("tool_calls", [])),
    }


def evaluate(task_file, out_csv):
    with open(task_file, encoding="utf-8") as f:
        cases = [json.loads(line) for line in f if line.strip()]

    rows = []
    with ThreadPoolExecutor(max_workers=MAX_WORKERS) as ex:
        futs = [ex.submit(run_one, c) for c in cases]
        for fut in as_completed(futs):
            try:
                rows.append(fut.result())
            except Exception as e:                 # 一条炸了不能带走整个评测
                rows.append({"id": "unknown", "success": False,
                             "reason": f"runner error: {type(e).__name__}: {e}"})

    rows.sort(key=lambda r: str(r["id"]))
    with open(out_csv, "w", newline="", encoding="utf-8") as f:
        w = csv.DictWriter(f, fieldnames=RECORD_FIELDS, extrasaction="ignore")
        w.writeheader()
        w.writerows(rows)
    return rows
```

注意 `evaluate` 里那个 `except Exception`。我一开始没加，结果某一条任务里 Agent 抛了个 KeyError，整个进程挂掉，前面跑完的 23 条结果一行都没落盘——因为它们还在内存里。那一刻我才明白，**结果必须边跑边落盘，或者至少保证一条失败不会带走全部**。上面的写法是次优解（结果仍在内存），更稳的做法是每条跑完立刻 append 一行到 CSV，你可以自己加，代价是文件句柄一直开着。

## 汇总函数：把 T7 的指标算出来

```python
def percentile(values, p):
    if not values:
        return 0.0
    s = sorted(values)
    idx = max(0, math.ceil(p * len(s)) - 1)
    return s[min(idx, len(s) - 1)]


def summarize(rows):
    n = len(rows)
    ok_rows = [r for r in rows if r.get("success")]
    durs = [r.get("duration_s", 0) or 0 for r in rows]
    total_cost = sum(r.get("cost_usd", 0) or 0 for r in rows)
    timeouts = [r for r in rows if "timeout" in (r.get("reason") or "")]

    print("[总览]")
    print(f"  task_success_rate : {len(ok_rows)}/{n} = {len(ok_rows)/n:.1%}")
    print(f"  cost_per_task     : {total_cost/n:.4f} USD   (分母={n})")
    print(f"  cost_per_success  : {total_cost/len(ok_rows):.4f} USD   (分母={len(ok_rows)})" if ok_rows
          else "  cost_per_success  : n/a（没有成功任务）")
    print(f"  p50 / p95 latency : {percentile(durs,0.5):.1f}s / {percentile(durs,0.95):.1f}s")
    print(f"  timeout_rate      : {len(timeouts)}/{n} = {len(timeouts)/n:.1%}")

    for field in ("type", "difficulty"):
        print(f"\n[分组] 按 {field}")
        buckets = {}
        for r in rows:
            buckets.setdefault(r.get(field) or "-", []).append(r)
        for k in sorted(buckets):
            g = buckets[k]
            g_ok = sum(1 for r in g if r.get("success"))
            g_dur = [r.get("duration_s", 0) or 0 for r in g]
            print(f"  {k:<10} {g_ok}/{len(g)} = {g_ok/len(g):6.1%}   "
                  f"avg {sum(g_dur)/len(g):5.1f}s   p95 {percentile(g_dur,0.95):5.1f}s")

    print("\n[失败原因 TOP]")
    reasons = {}
    for r in rows:
        if not r.get("success"):
            key = (r.get("reason") or "unknown").split(":")[0]
            reasons[key] = reasons.get(key, 0) + 1
    for k, v in sorted(reasons.items(), key=lambda x: -x[1]):
        print(f"  {v:>2}  {k}")


if __name__ == "__main__":
    rows = evaluate("testcases.jsonl", "results.csv")
    summarize(rows)
```

汇总里那几个名字——**Task Success Rate（任务成功率）**、**P95 Latency（95 分位延迟）**、**Cost per Task（单任务成本）**（均详见 TA 篇）——在 T7 里都定义过了，这里只讲怎么读。

63.3% 这个数本身没什么可看的。有意思的是下面几件事。

**第一，失败集中在哪。** email 类 57.1%，search 类 84.6%，hard 难度只有 28.6%。这说明周报助手的短板不在"查资料"，在"查完之后把它变成一封合规的邮件"。这两个问题要改的地方完全不同——前者是检索策略，后者是输出格式约束和工具调用的收口逻辑。

**第二，失败原因能不能聚成类。** "未调用工具" 5 次排第一，而且看 `tools_called` 列，好几个走到 `summarize` 就停了——它把邮件内容写好了，然后就没然后了。这是个非常集中的 bug，一个 prompt 补充或者一个强制收口的工具调用就能修掉一批。说白了，5 道题的失败是同一个原因，不是 5 个原因。

**第三，有没有行为异常的行。** wr-005 跑了 9 步、`tools_called` 里连着三个 `read_doc`，最后超时。这不像"任务难"，更像在兜圈子。T19 讲 Trace 归因时会专门处理这种，现在你至少能把它标记出来。

**第四，成本的两个分母。** `cost_per_task` 0.0528，`cost_per_success` 0.0834，比值 1.58——你每花 1 块钱，有 3 毛 7 是在为失败买单。这个比值比单独的任何一个成本数字都更能推动改动。

**第五，成功的行也要抽几条看。** 规则判定有个老毛病：它只能判你写进去的条件，写在条件之外的东西它一律放行。周报助手有一条判成功的任务，我点开 `tools_called` 一看，是 `search_web|send_email`——它压根没查内部文档，直接拿搜索引擎的结果编了一份"上周销售数据"就发出去了，而我的 `must_contain` 里写了"销售额"和"环比"，它俩都在，于是判成功。这种"蒙对的"任务在规则层是抓不到的，得靠抽查或者后面的模型裁判（详见 T12）。所以我现在的习惯是：每轮跑完随机抽 3 条成功任务人工看一眼，花五分钟，能救回一次尴尬的上线。

## 先用假 Agent 把脚本本身跑通

接真模型之前，先塞一个行为可预测的假 Agent 进去，确认整条链路是通的：

```python
def fake_agent(case, llm=None):
    """不调模型，行为固定，专门用来验证脚本本身。"""
    return {
        "answer": "销售额 120 万，环比 +8%。",
        "tool_calls": ["search_internal", "send_email"],
        "usage": {"prompt_tokens": 1000, "completion_tokens": 200},
        "steps": 4,
    }
# 跑通后：run_agent = fake_agent 替换成你自己的实现
```

这么做的理由很实在：先用真模型跑，一旦结果不对，你分不清是 Agent 的问题、判定器的问题，还是汇总函数的问题。用假 Agent 跑一遍，期望输出是确定的——30 条里应该成功几条、成本应该是多少，你心里有数。对得上，说明框架这边没问题，剩下的锅都在 Agent 身上。P2 会把这套 mock 做完整，这里只是个两分钟的简化版。

## 三个常见翻车

**超时没处理，整个评测卡死。** 开头那个 4 分钟就是这么来的。解法就是 `run_with_timeout`，但有个坑：Windows 上没有 `signal.alarm`，别指望它；用 `ThreadPoolExecutor` 包一层时，退出必须 `shutdown(wait=False)`，用 `with` 语句会一直等那个卡死的线程，超时等于没设。

**并发打满被限流。** 我第一次把 `MAX_WORKERS` 设成 32，结果一半任务返回 429，判定器老老实实把它们判成失败，成功率直接掉了二十几个点——其实那批是限流，不是 Agent 的锅。建议从 4 起步，并且在 `reason` 里把限流错误单独标记（`rate_limit`）不计入失败，或者至少重试一次再计入。这两件事必须分开统计，否则你的成功率里混着"我打太狠了"。

**没设花钱上限。** 这个我只在别人身上见过一次，一次就够了。Agent 死循环的时候，它不会自己停下来——它会一直调模型、一直烧 Token，直到你信用卡那边发来提醒。加个预算熔断很便宜，几行的事：在 `run_one` 里累计 `total_cost`，超过 `MAX_BUDGET_USD` 就直接抛异常中止整轮。另外给 Agent 本身设一个最大步数（比如 15 步），步数超限判失败并记 `reason="max_steps_exceeded"`，这同时也是循环检测（详见 T23）最朴素的形态。

**忘记记录失败原因。** 这个最隐蔽。周末跑完 63.3%，周一回来想复盘，打开 CSV 发现 `success` 列全有、`reason` 列全空，因为当初嫌麻烦没写。你只能把 11 个失败任务重跑一遍——而重跑的结果还不一定跟周末一样（这是下一篇 T9 的事）。`reason` 这一列是判定器里最该认真写的东西，比判定本身的优先级还高。

## 什么时候该重试，什么时候重试是白扔钱

脚本能跑之后，下一个问题很快就来了：一批跑完，七八条是红的，怎么办。重跑呗。

先分清楚红的两种红法，它俩的处理方式是相反的。

**第一种是执行出错。** 超时、网络错误、服务端 5xx、限流 429——这类该重试，重试通常能恢复。我现在的参数是：

```python
TIMEOUT_S = 120      # 单条用例超时保护，别让一条卡死拖到天亮
MAX_RETRY = 2        # 异常最多重试 2 次
RETRY_SLEEP_S = 3    # 每次间隔 3 秒
```

重试 2 次没什么玄学，就是试出来的：大部分偶发故障一次就回来了，第三次还是红的，基本可以断定它不是偶发。

**第二种是判定不通过。** 裁判说这条能力不行——不要重试。

说白了，这不是偶发故障，是能力问题。重试只是把同一道题多答一遍，除了多花一份钱，不会改变结论。我一开始就是不分青红皂白整批重跑，一次三十多块，跑完数字几乎没动。这钱花得冤。

唯一的例外：你本来就在做多次运行的一致性统计，每道题就是要跑 N 次看波动——那是另一回事，T10 会讲。

再补两条工程经验。

**并发别拉满。** 上面代码里 `MAX_WORKERS = 4` 是我随手拍的，你自己跑的时候建议从 3 个并发起步。太高会触发 API 限流，一堆 429 回来反而更慢（上一节那个坑）；太低，30 条一批要跑十几分钟，你就不愿意频繁跑了，而"愿意频繁跑"这件事本身比并发数重要。这个数字要在你自己账号的限流上限下试出来，别照抄我的。

**超时保护必须有。** 不给单条用例设上限，一条卡死的用例能把整批评测拖到天亮——开头那个 4 分钟就是这么来的。我后来把它从 60 秒提到了 120 秒：60 秒对复杂任务有点紧，会把本来能跑完的题判成超时。但 120 秒是上限不是目标，超了就记 `timeout`，然后交给上面那套重试逻辑。实现方式还是 `run_with_timeout` 那个 `ThreadPoolExecutor` 包装，Windows 下尤其别忘了 `shutdown(wait=False)`，代码不重复贴了。

## 第一版要丑，但要能跑

回头看这份脚本，它有十处可以改进：结果没边跑边落盘、判定器写死在代码里、没有缓存、没有断点续跑、并发策略是拍的、`llm_client` 还要你自己接。

这些都可以后补。第一版真正的门槛只有一个：今晚能不能跑出那张 CSV。跑出来，你就有了一个可以拿去跟人争论的东西；跑不出来，你手上就只有一个想法。

P1–P4 会把这些零件逐个规范化——数据结构先定死（P1）、mock 工具和确定性判定器（P2）、接 Judge 和统计汇总（P3）、出报告和接 CI（P4）。现在这份脚本里 `RECORD_FIELDS` 和 `judge()` 这两个，最后会原样搬进 P1 的 `TestCase` 和 P2 的规则判定层，所以这两处稍微写规矩一点是划算的。

## 一句话结论

先跑出一张能读的 CSV，再谈架构；判定器的 `reason` 列比判定结果本身更值得认真写。

下一篇要解决的麻烦是：你跑完拿到 80%，晚上手贱又跑了一次，变成 72%，代码一行没改——这个数字本身就不稳，那 80% 到底能不能拿去汇报。
