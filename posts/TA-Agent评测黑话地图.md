# Agent 评测黑话地图：一张能回查的术语手册（持续更新）

上周我在一个 Agent 群里围观了一场对话。有人问"我这个周报 Agent 成功率 84% 算高吗"，下面瞬间炸了：有人回"你 Pass@k 多少"，有人问"Judge 校准过没有"，还有人甩了句"样本量多少，置信区间报一下"。提问的老哥半天没吭声，最后发了个表情包退场。

这事儿烦就烦在：这些词单个拎出来都不难，难在没人给一张对照表，搜完还发现各家用法对不上。这篇就是那张表。

用法说明：不用从头读，收藏当字典。七大类各配一张速查表，表后把最容易混的几组单独讲透。后面每篇术语首次出现都会链回这里——卡住了就回来查。

举例统一用系列主线案例「周报助手」：能联网搜资料、读内部文档、最后发邮件的 Agent。

## 一、评测基础与数据集

| 名词（中英） | 一句话人话解释 | 常见误解 / 易混点 |
|---|---|---|
| Benchmark（基准测试） | 用标准化任务、数据和评分规则衡量 Agent 能力的一整套东西 | 不只是"一堆题"，还含环境与评分方法；排行榜（Leaderboard）分高 ≠ 你的场景好用 |
| Evaluation Dataset（评测数据集） | 专门拿来测 Agent 的任务集合 | 重点不是量大，是覆盖度、难度分布和代表性；50 条杂牌题不如 30 条设计过的题 |
| Ground Truth / Reference Answer（真实标注 / 参考答案） | 判断输出对不对的参照物；精选的核心题叫 Golden Dataset（黄金数据集） | 开放式任务没有唯一标准答案，参照物可以是约束、参考证据或评分细则 |
| Expected Outcome / Acceptance Criteria（期望结果 / 验收标准） | 把"算成功"写成可判定条件的描述 | 别只写结果不写约束——"发出了邮件"和"只发给组内三人"是两个验收项 |
| Task Taxonomy（任务分类体系） | 按类型、复杂度、工具需求、风险级别给任务贴标签 | 不贴标签的后果：一百条题全是单轮问答，多步能力没测到 |
| Data Leakage / Contamination（数据泄漏 / 污染） | 测试题混进了训练或调参过程，分数失真 | Agent 场景花样更多：题被模型背过、网页内容变了、调 prompt 的题和打分的题没分开 |

## 二、执行过程与轨迹

| 名词（中英） | 一句话人话解释 | 常见误解 / 易混点 |
|---|---|---|
| Agent Trace（执行轨迹） | 一次运行里模型调用、工具调用、返回结果、错误的完整记录 | 跟日志（log）不是一回事——Trace 结构化、能按任务串起来，破案全靠它 |
| Span / Trace Context（调用片段 / 追踪上下文） | Span 是一次具体操作（一次 LLM 请求或工具执行）；Context 把同任务的多个 Span 串成链 | 只记 Span 不记 Context，多步任务就散成孤立点 |
| Tool Calling / Function Calling（工具调用 / 函数调用） | Agent 选工具、填参数、处理返回值的整套动作 | 拆三件事看：Tool Selection（选对没）、Argument Accuracy（参数对不对）、Tool Error Rate（失败率） |
| Retry / Recovery（重试 / 故障恢复） | 工具报错、超时、返回异常时，Agent 能不能合理收场 | 会重试 ≠ 会恢复；无限重试是病，得配 Loop Detection（循环检测）和 Fallback（降级） |

## 三、评测指标与评分方法

| 名词（中英） | 一句话人话解释 | 常见误解 / 易混点 |
|---|---|---|
| Task Success Rate（任务成功率） | 满足预设成功条件的任务占比 | 跟 Goal Completion Rate 常混，见下方第 2 组 |
| Goal Completion Rate（目标完成率） | 任务目标及所有约束是否全部满足的占比 | 同上 |
| Pass@k | 跑 k 次，至少成功一次的概率估计 | 跟 Pass^k 常被张冠李戴，见下方第 1 组 |
| Pass^k | 跑 k 次，次次都成功的概率估计 | 同上 |
| Exact Match（精确匹配） | 输出和标准答案一字不差 | 只适合封闭式答案；拿它判周报内容会难看到失真 |
| Precision / Recall / F1（精确率 / 召回率 / 综合值） | 分类、抽取类任务的经典三件套 | 拿来评开放式生成不合适，别硬套 |
| Rubric-based Scoring（评分细则打分） | 按写明的细则逐项给分 | 细则没写锚点示例等于没写，裁判各打各的 |
| Pairwise Comparison（成对比较） | 两个候选结果放一起判哪个好 | 省掉绝对标准，但引入位置偏差，见第四类 Position Bias |
| Cost per Task（单任务成本） | 完成一个任务平均花多少钱 | 只报成功率不报成本的结论不完整 |
| Latency / P95 Latency（延迟 / 95 分位延迟） | 执行耗时，以及最慢那 5% 的门槛 | 平均值会骗人——用户记住的永远是最慢那次 |
| Token Usage（Token 消耗） | 一次任务吃掉多少输入输出 token | 成本的主要构成，循环失控时第一个暴涨的就是它 |
| Robustness（鲁棒性） | 输入扰动、异常、边界条件下性能稳不稳 | happy path 全过不代表鲁棒，得靠故障注入测（T22） |
| Calibration（校准） | 置信度和实际正确率的一致程度 | 说"90% 确定"的题真对了 90% 才算好；Judge 语境另有含义，见下方第 3 组 |

### 易混概念 ①：**Pass@k vs Pass^k**

这俩长得像，意思几乎相反：

- **Pass@k**：给 k 次机会，**至少中一次**就行——"多试几次能不能碰出来"。
- **Pass^k**：跑 k 次，**要求每次都成**——"它稳不稳"。

拿周报助手说：跑 5 次有 3 次成功发出合格周报，那 Pass@5 反映的是"多跑几遍总能拿到一份能用的"，而 Pass^5 是 0——你不敢让它无人值守。做 demo 时人们关心前者，做上线决策时该关心后者。我当时也这么以为：报告里写个 Pass@k 显得漂亮，后来才发现领导真正想问的是 Pass^k。

另外，不同论文的估计公式不完全一样，用时写清你的计算方法，别只甩一个数。

### 易混概念 ②：**Task Success Rate vs Goal Completion Rate**

不少项目把这俩混着用，统计口径一乱，报告都没法写。

区别在于约束算不算进去。Task Success Rate 看"预设成功条件满足没有"；Goal Completion Rate 强调"目标连同所有约束全部满足没有"。周报助手"搜了资料、写了周报、发了邮件"算 Task Success；"字数没超、格式合规、只发给组内三人、没抄送全公司"全满足才算 Goal Completion。

如果你的成功条件本来就把约束写全了，两者数值完全一样——那也行，但要在评测文档里写死定义，别来回换口径，更别同时报两个数让人以为你测了两样东西。

## 四、Judge LLM 与自动评测

| 名词（中英） | 一句话人话解释 | 常见误解 / 易混点 |
|---|---|---|
| LLM-as-a-Judge（大模型当裁判） | 用一个模型给另一个模型或 Agent 的输出打分 | 有论文背书的通行术语；贵、慢、会偏心，不是装上就完事 |
| Judge Agent（裁判 Agent） | 把模型判断、工具取证、复核流程组合起来的评测系统 | **工程说法，不是论文通行术语**——T16/T17 细讲，别拿它当行业标准吹 |
| Evaluation Rubric（评分细则） | 每个评分维度的标准写清楚的那份文档 | 没写锚点示例的 Rubric 约束力约等于零 |
| Reference-based Evaluation（基于参考的评测） | 有参考答案或证据，照着对 | 适用范围比想象窄，Agent 多数任务没有唯一答案 |
| Reference-free Evaluation（无参考评测） | 不靠标准答案，按约束和质量标准评 | "无参考"≠"没标准"，标准藏在约束和 Rubric 里 |
| Pairwise Judge（成对裁判） | 两个结果二选一判胜负 | 必须换序再判一遍，不然位置偏差吃掉结论 |
| Position Bias（位置偏差） | 裁判偏爱先出现或后出现的那个答案 | 成对比较头号坑，换序重判是最低成本的检查 |
| Verbosity Bias（长度偏差） | 裁判偏爱更长更详细的答案 | 周报写得越长分越高？可能只是裁判在吃字数 |
| Judge Agreement（裁判一致性） | 多个裁判对同一结果的判断一致程度 | 见下方第 3 组，一致性高不代表判得对 |
| Judge Accuracy（裁判准确率） | 裁判的判断跟可信参考标准符不符合 | 同上 |
| Judge Calibration（裁判校准） | 裁判的评分尺度和实际表现（或人工标准）对不对齐 | 同上 |
| Inter-rater Reliability（评审者间信度） | 多个评审者（人或模型）评分的可靠程度 | Agreement 的统计学说法，常用 Cohen's Kappa 等 |
| Human Evaluation（人工评测） | 人来打分，常用来校验自动评测 | 不是永动机——人也会累会飘，要双盲和对齐率管理 |
| Adversarial Evaluation（对抗性评测） | 用刁钻输入检验评测器和 Agent 靠不靠谱 | 既能测 Agent，也能测 Judge 会不会被绕 |

### 易混概念 ③：**Judge Agreement vs Judge Accuracy vs Judge Calibration**

三个词都在说"裁判靠不靠谱"，但各管一件事：

- **Agreement（一致性）**：几个裁判之间判得**一不一样**。
- **Accuracy（准确率）**：裁判的判断跟可信参考标准**对不对得上**。
- **Calibration（校准）**：裁判的评分尺度或置信程度跟实际表现**匹不匹配**。

关键一句话：**多个裁判给出相同的错误判断，一致性满分，准确率零分。** 三个裁判都说周报里那个编造的数据来源没问题——彼此完全一致，也一致地错了。评估 Judge 的顺序：先拿人工标注的小样本测 Accuracy，再看多 Judge 间的 Agreement，最后定期 Calibration 纠偏，别反。

## 五、统计可靠性与实验设计

| 名词（中英） | 一句话人话解释 | 常见误解 / 易混点 |
|---|---|---|
| Confidence Interval（置信区间） | 估计值的不确定性范围 | 严格说是"同样方法反复抽样，区间盖住真值的比例"，别讲成"真值有 95% 概率在区间里" |
| Statistical Significance（统计显著性） | 观察到的差异有没有足够统计证据 | 显著 ≠ 值得上线：只差 0.5% 的显著，业务上可能毫无意义 |
| Sample Size（样本量） | 评测用了多少条任务 | 想检出的差异越小样本要越大；30 条题分不出 2% 的差距 |
| Variance（方差） | 多次评测结果的波动程度 | 波动大的 Agent，单次结果几乎不能当结论 |
| Inter-run Variance（跨次运行波动） | 同一任务跑多次，结果的变化程度 | Agent 特有：温度、并发、工具超时、外部数据都在贡献波动 |
| Ablation Study（消融实验） | 拆掉某个模块看性能变化 | 一次只拆一个，拆三个就说不清是谁的功劳 |
| A/B Testing（A/B 测试） | 两个版本在可比条件下对比 | Agent 上比 Web 麻烦：输入不可控，延迟差异还影响体验 |
| Reproducibility（可复现性） | 相同条件下重跑能否得到相近结果 | 前提是记了环境快照——模型版本、参数、时间戳，缺一样复盘就断线 |
| Regression Testing（回归测试） | 检查新版本有没有让老能力退化 | 改一行 prompt 也要跑一遍，这不是仪式感，是血泪教训 |
| Contamination（数据污染） | 测试数据进了训练或调参过程，分数失真 | 即第一类的 Data Leakage，一词两译 |

一个典型场景：两个 Agent 成功率 82% 和 84%，仅凭这两个数不敢说谁更好——样本量小、随机性大，这 2 个百分点可能全是运气。同批任务上的版本对比用配对分析，独立样本用对应方法，别混。这组 T11 讲透。

## 六、安全性与可靠性评测

| 名词（中英） | 一句话人话解释 | 常见误解 / 易混点 |
|---|---|---|
| Safety Evaluation（安全性评测） | 测 Agent 会不会干出格的事 | 只测"该拒的拒没拒"不够，还得测"不该拒的别瞎拒"（过度拒绝，T25） |
| Prompt Injection（提示词注入） | 用恶意指令劫持 Agent 行为 | 注入源可能藏在待读邮件或网页里，不止用户输入 |
| Tool Misuse（工具误用） | 不当或错误地使用工具 | 包括"调了不该调的工具"，不只是参数填错 |
| Unauthorized Action（越权操作） | 执行了没被授权的操作 | 周报抄送全公司就是典型——动作"合法"，权限越界了 |
| Policy Compliance（策略合规） | 是否遵守系统策略和业务规则 | 规则要写进评测项，别指望模型自觉 |
| Data Exfiltration（数据外泄） | 未经授权提取或泄露数据 | 可以披着"正常工具调用"的外衣 |
| Robustness Testing（鲁棒性测试） | 输入扰动、异常返回、边界条件下表现如何 | 跟第三类 Robustness 一体两面：那是指标，这是测法 |
| Fault Injection（故障注入） | 人为制造超时、报错、垃圾返回，看恢复能力 | 最容易被跳过——happy path 跑通就想上线 |
| Human-in-the-loop（人工在环） | 高风险操作引入人工审核确认 | 触发条件没设计好会把人烦死——每封周报都人工确认等于没自动化 |
| Blast Radius（爆炸半径） | 出错时可能波及的范围 | 决定一个操作要不要人工在环的核心考量 |

一条工程原则单独加粗：**Agent 说自己没执行危险操作，不等于它真的没执行。** 评测能发邮件的 Agent，光看最终回答没用，要查邮件工具的实际调用记录、收件人、发送状态。安全验证逻辑，放在独立于模型判断的执行层。

## 七、生产环境与在线评测

| 名词（中英） | 一句话人话解释 | 常见误解 / 易混点 |
|---|---|---|
| Offline Evaluation（离线评测） | 用固定数据集在受控环境里评测 | 跟在线评测是闭环关系，见下方第 4 组 |
| Online Evaluation（在线评测） | 在真实运行或受控线上流量里评估 | 同上 |
| Shadow Testing（影子测试） | 候选版本旁路运行，不影响真实用户 | 只跑不生效，适合新版本上线前的第一关 |
| Canary Release（金丝雀发布） | 先放少量流量用新版本 | 比 Shadow 进一步：结果真生效，但波及面小 |
| Drift Detection（漂移检测） | 监测输入分布或系统表现随时间的变化 | 数据源变了、接口变了，分数悄悄掉，靠它报警 |
| Production Monitoring（生产监控） | 盯线上成功率、延迟、成本、异常 | 离线的指标在线上都要有对应物 |
| SLO / SLA（服务目标 / 服务等级协议） | 服务要达到的量化承诺 | SLO 是内部目标，SLA 是对外合同，违约含义不同 |
| Feedback Loop（反馈闭环） | 线上反馈和失败案例回流到评测集与优化流程 | 没有这条，离线题库会越来越脱离真实世界 |
| Observability（可观测性） | 通过日志、指标、追踪理解系统运行状态 | Trace 是基石——没记 Trace 谈不上可观测 |

### 易混概念 ④：**离线评测 vs 在线评测——不是二选一，是一个闭环**

很多人觉得"离线测完上线了，评测这事就结束了"。我当时也这么以为，直到线上第一周的失败案例跟离线题库里一条都不像。

离线好不代表线上好：用户输入更杂、工具会抖、数据天天变。成熟体系转的是一个圈：

1. **Offline Benchmark**：固定任务集 + 规则评测 + Judge LLM，改动先在这过一遍；
2. **灰度 / Shadow Testing**：新版本进受控环境，先观察不影响用户；
3. **Production Monitoring**：盯真实任务的成功率、成本、延迟和失败；
4. **Failure Analysis & Dataset Update**：分析线上失败的 Trace，典型案例脱敏去重后入回归题库；
5. **回到离线评测**：验证改动是不是真的解决了捞回来的问题。

离线是在线的准入证，在线是离线的出题人。闭环的每一环，T26–T28 拆开给做法。
