# 指标别贪多：我列过 11 个，最后常看的只有 3 个

我给周报助手列过 11 个指标。

任务成功率、目标完成率、单任务成本、P95 延迟、Token 消耗、工具调用准确率、跨次运行波动、错误恢复率、拒绝率、用户满意度打分，还有一个我自己拍脑袋造的"信息完整度"。

三个月后回头翻记录，常打开的只有 3 个。

剩下那 8 个算得都没错，问题出在别处——要么跟别的指标高度重合，要么数字动了我也不知道该去改哪一行代码。（顺带吐槽一句，"信息完整度"这种自己造的指标最尴尬：0.7 分到底算好还是算坏，我自己也说不清，最后它变成了一个谁都不敢引用只会让表格变长的东西。）

这事儿烦就烦在：指标列得越多，汇报的时候反而越难开口，因为你得先花五分钟解释这 11 个之间是什么关系，而听的人只想要一句话的答案。

所以这篇不打算给你一份"必看指标大全"。我想做三件事：把指标分成三层、讲清哪一对最常被当成两个其实是一个、然后给你一张挑指标的决策表和一份能直接抄的指标字典。

## 先分三层，再谈挑几个

指标堆在一张平铺的清单里是没法挑的。先按"它回答什么问题"分三堆，取舍立刻就容易了。

**正确性类**——这件事到底办成了没有。

- **Task Success Rate（任务成功率）**（详见 TA 篇）：满足预设成功条件的任务比例。
- **Goal Completion Rate（目标完成率）**（详见 TA 篇）：任务目标及各项约束是否全部满足。

**效率类**——办成这件事代价多大。

- **Cost per Task（单任务成本）**（详见 TA 篇）：完成单个任务的平均成本。
- **Latency / P95 Latency（延迟 / 95 分位延迟）**（详见 TA 篇）：任务耗时的分布，P95 就是排在 95% 位置上的那个值，也就是"最慢的那一小撮"有多慢。
- **Token Usage（Token 消耗）**（详见 TA 篇）：一次任务里输入加输出的总量。

**可靠性类**——下次再来一遍，还行不行。

- **Inter-run Variance（跨次运行波动）**（详见 TA 篇）：同一批任务跑多次，结果的变化程度。
- **Error Recovery Rate（错误恢复率）**（详见 TA 篇）：工具报错、超时之后，Agent 能自己爬起来并继续把事办完的比例。

说白了，这三层对应三个不同的人问的三个问题：产品问办成了吗，运维问花了多少钱多久，你自己问明天还能不能这样。

我一开始把"工具调用准确率"也归进了正确性那一层，后来发现它在多数场景下跟任务成功率高度相关——工具调错了，任务几乎一定失败，两个数一起汇报等于把同一件事说两遍。它真正的用武之地是失败归因（详见 T19、T21），不是汇报。

## Task Success Rate 和 Goal Completion Rate，很多人当成两个指标在报

这是全系列最容易混用的一对，值得单独拆开讲。

先说大家为什么会觉得它是两个东西。直觉上，"任务成功"听起来像"跑完了没崩"，"目标完成"听起来像"用户要的东西都齐了"，后者明显要求更高。按这个直觉，前者数值应该高于后者，于是很多人同时报两个：TSR 82%，GCR 71%，看起来信息量翻倍。

问题在于，这个区分是你自己定的，不是指标自带的。

任务成功率的分母和分子，完全取决于你在 T6 那篇里写下的成功条件。如果你的成功条件已经把所有目标约束都写进去了——比如"邮件已发送、收件人正确、包含三个数据源的结论、字数不超过 500"——那么满足它的任务比例，与"目标及约束全部满足"的比例，在数学上是同一个数字，一格不差。

我当时就是这么踩的坑。周报助手第一版评测里，TSR 是 82%，GCR 是 79%，我盯着这 3 个点差琢磨了大半天，翻遍日志想找出"跑完了但目标没达成"的那批任务，最后发现问题出在我自己写的判定器上：邮件那一项少判了一个收件人字段，三道题因此掉了 GCR 却没掉 TSR。把那一处补上，两个数变成一模一样的 82%。

所以正确做法只有一条：建评测的时候，先把两个定义各写一句话钉死，写在哪儿都行，写在 README 里最好。

我现在的钉法是这样的：

- **Task Success Rate**：判定器里 `success_criteria` 全部为真的任务占比，分母是所有任务。
- **Goal Completion Rate**：只在判定分级的时候才单独算——把"核心目标达成"和"附加约束达成"拆成两档，GCR 就是两档都为真的占比。

这么拆完，GCR ≤ TSR 恒成立，两个数并列汇报才有意义。如果你把成功条件写成了一整块不分级，那就只报一个，别硬凑两个数字来制造信息量。

一句话记住：**两个指标要么定义不同，要么数值相同**。数值不同又说不清差在哪，那多半是判定器有 bug，不是 Agent 有问题。

## 按场景挑三到五个：一张决策表

全上是默认选项，也是最偷懒的选项。下面这张表是我现在用的挑法。

| 你现在要解决的问题 | 首要指标 | 必须一起看的 | 可以先不管的 |
|---|---|---|---|
| 内部 demo，只想证明"能跑通" | Task Success Rate | 失败任务列表 | 成本、P95、跨次波动 |
| 选模型 / 挑 prompt 版本 | Task Success Rate | Cost per Task、P95 Latency | 错误恢复率 |
| 准备上线，评估扛不扛得住 | Task Success Rate | P95 Latency、Inter-run Variance | Token Usage（已被成本含住） |
| 上线后成本超预算 | Cost per Task | Token Usage、Task Success Rate | 跨次波动 |
| 用户投诉"有时候好有时候烂" | Inter-run Variance | Error Recovery Rate、P95 Latency | 平均成本 |
| 要对外汇报 / 写进材料 | Task Success Rate + 样本量与口径说明 | Cost per Task、P95 Latency | 所有你自己造的指标 |

最后一行那个"样本量与口径说明"别嫌啰嗦，一个光秃秃的百分比拿出去汇报是危险的，为什么危险 T11 会专门讲。

挑的原则只有一条：**每个指标都要对应一个你会做出的决定**。想不出"这个数字变了我要去改哪"的指标，先别列。

有人问我"三个够不够"，我的回答是看阶段。刚起步就三个：成功率、单任务成本、P95 延迟。等你的任务集过了 50 条、开始做版本对比，再把跨次波动加进来——那时候没有它你已经吃过亏了。

## 一条用例到底算不算通过：别让所有打分做 AND

跑完一条用例，五个裁判（Judge）各自给分——内容对不对、有没有编造、该覆盖的点覆盖了没、工具调得对不对、格式遵不遵循——然后你要求"五个全过才算过"。

听着特别严谨。我一开始也这么干，跑出来成功率 41%，拿着这个数去改 Agent，改了两周改不动。因为那 41% 里混着两种完全不是一回事的东西：内容全对但没分段的，和内容全错但排版完美的。它们在这张表里长得一模一样。

举个具体的。周报助手有一条用例，三个来源全查到了，结论也对，唯一的问题是回复没按参考输出那样分段，写成了一大坨。这时候**格式遵循（Format Adherence）**判不通过，但"任务完成"是通过的。你因为排版问题把一份内容正确的周报判成失败，这个通过率就不反映真实能力了，它反映的只是你的排版要求有多严。

说白了，把所有打分做 AND，等于让最弱的那个维度替所有维度拍板。

正面做法是：每一类评测只挑一个**主指标（Primary Metric）**，用它唯一决定这条用例过不过。其余指标一律不参与通过判定，降级成**诊断指标（Diagnostic Metrics）**单独统计，用途只有一个——回答"如果不过，是卡在哪"。

| 评测范围 | 主指标 | 为什么选它 |
|---|---|---|
| 整体评测 | 任务完成率 / 任务成功率 | 用户只在乎事办没办成，其余都是过程 |
| 意图 / 路由评测 | 意图准确率（Intent Accuracy）或路由准确率（Routing Accuracy） | 这一步错了后面全白跑，必须单独拎出来先看它 |
| 记忆评测 | 记忆保留率（Memory Retention Rate） | 它衡量的就是"上一轮说过的还记不记得"，跟这一轮答得好不好无关 |
| 工具评测 | 工具调用准确率（Tool Call Accuracy） | 选错工具比参数写错严重得多，先盯这一个 |
| 异常输入评测 | 异常处理率，不是完成率 | 输入本身就是脏的，正常完成不该是考核目标，稳住不崩才是 |

最后一行最容易写反。给一句乱码、一段超长文本、一句带越权请求的话，你还拿任务完成率当主指标，那批用例的成功率会低得毫无意义——这类输入本来就不该被完成。这时候该看的是它有没有稳住、有没有按规矩拒掉。

记住一句就够了：主指标不是唯一的指标，是"用来拍板的那一个"。这句话我抄在了 README 第一行。

## 指标自查清单：六个最常见的错误解释方式

这块是本篇真正想让你带走的东西。指标算得对不是一回事，解释得对不对是另一回事，后者出事的概率高得多，而且出事的时候没人会发现。

**① 拿单次运行结果当能力。**

周报助手跑了 30 道题，其中一道是"把上周销售数据整理成邮件发给张总"，这次它成功了，于是你说"发邮件这类任务没问题"。

一道题一次结果，样本量是 1。它证明的唯一事情是"这道题存在一条能走通的路"。能叫能力的说法是"发邮件这个标签下 14 道题，成功率 57%"。

**② 把多次尝试的最好成绩当水平。**

同一个任务跑了 5 次，其中最好的那次完美无缺。有人会据此写"该任务已通过"，或者更隐蔽一点——把最好的那次结果拿去汇报。

这个口径 T10 会展开，这里先给结论：最好成绩对应的是 **Pass@k（多次尝试中至少一次成功的概率估计）**（详见 TA 篇），稳定成绩对应的是 **Pass^k（多次尝试均成功的概率估计）**（详见 TA 篇）。这俩数可以差得非常远，汇报时必须写清你报的是哪一个。

**③ 用平均值掩盖长尾。**

P50 好看但 P95 崩了，是最容易漏掉的一种失败。周报助手平均耗时 18 秒，听着挺快；P95 是 94 秒，也就是说每 20 个任务里有 1 个要等一分半。而用户记住的恰恰就是那一分半。

延迟类指标我现在的习惯是永远成对报：P50 + P95，只报一个等于没报。

**④ 指标之间高度重合还在并列汇报。**

前面那对 TSR / GCR 就是典型。还有一对常见的是 Cost per Task 和 Token Usage——如果你的成本完全由 Token 决定（没调外部付费 API、没算人力），这两个是线性关系，一起报纯属重复占版面。

检查方法很土但有效：把两个指标的历史数据扔进表格算个相关系数，绝对值超过 0.9，留一个就行。

**⑤ 分母不清。**

"平均成本 0.8 元/任务"——这个 0.8 的分母里，包不包含失败的任务？

包不包含差别巨大。失败的任务往往更贵：它卡住了、重试了、死循环了，Token 烧得比一次顺利跑完多得多。只统计成功任务，成本会被系统性低估，而且版本越烂、失败率越高，被低估得越狠，最后你会得出一个荒谬的结论——"这个更差的版本单位成本更低"。

两个都算才是对的：

- `cost_per_task`（分母 = 全部任务）：这是你下个月真正要付的钱。
- `cost_per_success`（分母 = 成功任务）：这是"办成一件事的单价"，用来做 ROI 判断。

这俩的比值本身就是个好指标：它升高说明你在为失败付钱。

**⑥ 上游错了的时候，下游指标要跳过，不要连坐。**

这条是我踩得最狠的一条。

周报助手有一条用例，期望走"查内部文档"这条路。结果 Agent 把它错判成要发邮件，链路本身就走岔了，检索那一步压根没执行。

麻烦跟着来了。我有几个指标是依赖"检索到的原文"才能算的：有没有编造，也就是**忠实度（Faithfulness）**；该覆盖的知识点覆盖了没，也就是**覆盖率（Coverage）**。原文都没有，这俩指标根本没有执行机会。再加上工具调用准确率，一共三项，照常判的话全部记失败。

可它们衡量的是检索和生成的能力，压根没跑起来，判它失败是冤枉的。更糟的是这种冤枉会稀释平均值：一批用例路由错了之后，忠实度跟着掉十几个点，你一看曲线以为生成变差了，跑去调 prompt，调半天调不动，根因其实在路由那一层。这钱花得冤。

做法就一句话：**执行判定前先检查前置条件成不成立，不成立就标记成 error 跳过统计，既不计分子也不计分母。**

具体点：忠实度、覆盖率这类指标，先确认 `retrieved_docs` 非空、且 `route == expected_route`；不成立就把这条用例在该指标上的状态写成 `error`，汇总的时候分母里不数它。这样路由的错误只体现在路由准确率那一个数上，不会雪崩式污染别的数据。

一句总结：**指标各司其职，一个地方出错别让全班扣分。**

## 指标字典：直接抄

下面这份是我现在在用的，YAML 格式，每个指标四件套：定义、算法、适用场景、常见误读。字段名跟下一篇 T8 脚本里输出的 CSV 列名对得上，可以无缝接。

```yaml
metrics:
  - id: task_success_rate
    name: 任务成功率（Task Success Rate）
    definition: 判定器判定 success_criteria 全部为真的任务占比
    formula: count(success == true) / count(all_tasks)
    denominator: 所有已执行的任务（含超时、含异常，不得静默剔除）
    applies_to: [版本对比, 上线评估, 对外汇报]
    common_misread: 单次运行结果不等于成功率；分母不清会导致失败任务被悄悄丢掉

  - id: goal_completion_rate
    name: 目标完成率（Goal Completion Rate）
    definition: 核心目标与附加约束均被满足的任务占比
    formula: count(core_ok and constraints_ok) / count(all_tasks)
    denominator: 所有已执行的任务
    applies_to: [约束较多的任务, 分级判定]
    common_misread: 若成功条件已包含全部约束，本指标与 task_success_rate 数值相同，无需并列汇报

  - id: cost_per_task
    name: 单任务成本（Cost per Task）
    definition: 完成单个任务的平均成本
    formula: sum(cost_usd) / count(all_tasks)
    denominator: 所有已执行的任务
    applies_to: [预算评估, 成本优化]
    common_misread: 分母排除失败任务会系统性低估成本，失败率越高低估越严重

  - id: cost_per_success
    name: 成功任务单价
    definition: 每办成一件有效任务的平均成本
    formula: sum(cost_usd) / count(success == true)
    denominator: 仅成功任务
    applies_to: [ROI 判断, 版本性价比对比]
    common_misread: 不能单独用来评估总支出，必须与 cost_per_task 一起看

  - id: p95_latency
    name: 95 分位延迟（P95 Latency）
    definition: 任务耗时分布中第 95 百分位的值
    formula: sorted(durations)[ceil(0.95 * n) - 1]
    denominator: 所有已完成的任务（超时的单独计入 timeout_rate）
    applies_to: [上线评估, 体验优化]
    common_misread: 只报 P50 会漏掉长尾；P95 与超时率必须分开统计，否则超时被截断后 P95 会假性变好

  - id: token_usage
    name: Token 消耗（Token Usage）
    definition: 单任务输入 + 输出 Token 总量
    formula: sum(prompt_tokens + completion_tokens) / count(all_tasks)
    denominator: 所有已执行的任务
    applies_to: [成本归因, 循环检测]
    common_misread: 与 cost_per_task 常高度相关；若成本仅由 Token 决定则不必并列汇报

  - id: inter_run_variance
    name: 跨次运行波动（Inter-run Variance）
    definition: 同一任务集多次运行，成功任务数的离散程度
    formula: stddev(success_count_per_run)，必须与"重复运行次数"一起写
    denominator: 运行次数（>= 3 才有意义，2 次之间无波动不代表稳定）
    applies_to: [稳定性评估, 版本对比前的可行性判断]
    common_misread: 只跑两次就下结论；把波动当成"模型变好了"而不查别的原因

  - id: error_recovery_rate
    name: 错误恢复率（Error Recovery Rate）
    definition: 工具报错或超时后，Agent 自行恢复并最终成功的比例
    formula: count(recovered_after_error) / count(tasks_with_error)
    denominator: 出现过至少一次工具错误的任务（不是全部任务）
    applies_to: [工具依赖重的 Agent, 故障注入评测]
    common_misread: 分母写成全部任务会把指标稀释到看不出变化；"恢复"需预先定义（重试成功？换工具成功？还是老实报错也算？）
```

别急着整份抄进去。先照着前面那张决策表挑三个，跑两周，等你真的因为某个数字改变过一次决定，再把它留下。留下的才是指标，留不下的只是报表装饰。

## 一句话结论

指标的价值不在数量，在于每个数字背后都站着一个你会做出的决定，以及一个你写清楚了的分母。

下一篇要解决的麻烦很具体：定义写好了、指标挑完了，怎么把它变成一份双击就能跑的 Python 脚本——并且跑完之后，那张结果表到底该怎么读，尤其是不只盯着最底下那个百分比。

你给 Agent 定指标时踩过什么坑？特别是那种"数字很好看、后来发现是假的"的情况，评论区聊聊，我攒够一批写进番外 F2 的错题本。
