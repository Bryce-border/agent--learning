# 把公开数据集改成自己的：从抄题到出题

我干过这么一件事：从网上扒了一个公开的 Agent 评测集，五百多道题，直接拿去给周报助手跑。跑出来 91%。我拿着这个数字去汇报，被问了三个问题，一个都答不上来：

"这五百道题里有多少道跟你的业务有关？""这些题公开多久了，模型是不是背过？""你调 prompt 的时候用的是不是也是这批题？"

三个问题，一个比一个致命。最后那个 91% 被我从汇报里撤了下来。说白了，公开数据集不能直接拿来打分，它顶多是个素材库。这篇讲怎么把素材变成题。

## 题的三个来源，各自有脾气

先认清楚你的题能从哪里来。三条路，没有一条是免费的。

**真实日志。** 从你 Agent 的线上运行记录里挑案例。优点是真实，这就是用户真实会干的事；缺点也是真实——脏，要脱敏，要清洗，而且分布严重偏斜，高频任务占九成，长尾那些"一年发生一次但一出事就是大事"的任务全挤在角落。还有个小尴尬：日志里的任务是"它已经见过的"，拿来测新版本，测的是"改进"，测不出"能力边界"。

**手工构造。** 你自己或者团队坐下来出题。优点是可控，想测什么能力就造什么题；缺点是慢，一个人的出题速度大概是一下午五到十道，而且出题人的盲区会变成题库的盲区。我第一周出的题，后来翻出来看，清一色都是"我自己觉得它会错"的地方——它真正常错的地方我一个都没料到。

**公开数据集改造。** 拿 GAIA、WebArena 这类公开题当素材，照着你的场景改。优点是快，题目结构是现成的，判定方式多半也想好了；缺点有两个：场景多半跟你的业务不贴，以及一个越来越大的问题——污染。这个后面专门讲。

实操里三样都用：真实日志定分布，手工构造补长尾，公开改造凑数量。只靠任何一条都不够。

## 让文档自动吐用例，但你得审

手工构造那条路有个提速版本。

一个人一下午五道题，攒两百条要多久？我算过，快一个月。我当时也这么做来着，硬憋到第三周，题才四十来条，人先扛不住了。后来换成半自动：让模型直接读内部文档，吐结构化用例，人只管审。生成（Generation）→ 人工审核（Human Review）→ 入库，这条流水线把出题速度提了好几倍，后面一周入库一百多条不费劲。

做法本身不复杂，文档切片喂进去，让它按字段吐 JSON。麻烦全在下面这三条提醒上。

**第一，生成的题不能直接进评测集。** 质量参差不齐是常态。最要命的是那种题面看着漂亮、参考答案写错的——它会把整场评测带到沟里去：Agent 答对了反而扣分，你还会以为是自己 Agent 的问题。我吃过这个亏。一次性灌了两百条生成题进测试集，分数难看得不行，查了一整天才发现有三成参考答案是错的，跟 Agent 一点关系没有。审核最少盯两样：题面用你手头的文档和工具是不是真能答出来，参考答案是不是真的对。我在数据结构里留了个 `reviewed` 字段，没过审的不许进库，靠这个字段硬卡。

**第二，不同类型的题要下不同的生成要求。** 别指望一份 Prompt 打天下，出来的东西会是一个味道。知识问答类，要它连"应该检索到的知识点清单"一起给出来，不然你根本没法判断它到底查对了没有；工具调用类，要它给"正确的调用参数"，光来一句自然语言描述是判不了的；多轮类，要它写明每一轮，并标出哪一轮必须引用历史。要求给得越具体，后面审起来越省事。

**第三，负面用例（Negative Case）单独补。** 这条最容易被漏掉。模型特别擅长编顺着说的题，不擅长编刁难自己的题——它吐出来的东西整体偏简单、偏正面，清一色"文档里有、问得清楚、答得完整"。可真正让 Agent 翻车的常常在另一头：问了个文档里压根没有的东西，它一本正经编了一段；问了个它不该答的东西，它照答不误。这类题得你自己写，或者在生成时下死命令让它专门造，比例我一般压到三成以上。

生成用的 Prompt 骨架和最小实现长这样。模型调用统一封在 `llm_client` 里，换模型只改那一个文件：

```python
# llm_client.py —— 换模型/换 SDK 只动这个文件
# from YOUR_SDK import OpenAI

def chat(model, messages, temperature=0.0):
    client = YOUR_CLIENT  # 替换成你的 SDK 客户端
    resp = client.chat.completions.create(
        model=model, messages=messages, temperature=temperature
    )
    return resp.choices[0].message.content
```

```python
# generate_cases.py
# 用法：python generate_cases.py docs/weekly_guide.md knowledge 20
import json
import sys

from llm_client import chat

MODEL = "YOUR_MODEL_NAME"

# 每类评测集要的东西不一样，分开写要求
SPECS = {
    "knowledge": {
        "extra": ["must_retrieve"],          # 应该检索到的知识点清单
        "hint": "题目必须能在给定文档里找到答案，答案要能被原文片段支持",
    },
    "tool": {
        "extra": ["expected_call"],          # 正确的调用参数
        "hint": "给出工具名和完整参数，参数值必须能从题面推出来",
    },
    "multi_turn": {
        "extra": ["turns"],
        "hint": "2-5 轮，至少一轮包含指代或上下文引用，并标出是哪一轮",
    },
}

PROMPT = """你是评测用例生成助手。下面是内部文档片段：

<doc>
{doc}
</doc>

请基于它生成 {n} 条「{kind}」类评测用例。要求：
1. 每条包含字段：task / expected / source_quote / {extra}
2. {hint}
3. 题面写成真人会问的话，不要复述文档标题
4. 只输出 JSON 数组，不要任何解释

{negative}"""

NEGATIVE_RULE = (
    "补充要求：其中至少三成是负面用例——文档里没有答案、"
    "或答案存在但按权限不该回答，这类题的 expected 写'应拒答或声明未找到'。"
)

def build_prompt(doc, kind, n, negative=True):
    spec = SPECS[kind]
    return PROMPT.format(
        doc=doc[:4000],                       # 长文档先切片，别一股脑塞进去
        kind=kind,
        n=n,
        extra=" / ".join(spec["extra"]),
        hint=spec["hint"],
        negative=NEGATIVE_RULE if negative else "",
    )

def generate(doc_path, kind, n=20):
    with open(doc_path, encoding="utf-8") as f:
        doc = f.read()
    raw = chat(MODEL, [{"role": "user", "content": build_prompt(doc, kind, n)}], temperature=0.7)
    cases = json.loads(raw)                   # 模型偶尔吐不干净，外面记得套 try + 正则兜底
    for i, c in enumerate(cases):
        c["id"] = f"gen-{kind}-{i:03d}"
        c["source"] = "LLM生成-待审"
        c["reviewed"] = False                 # 审完手动改成 True 才允许入库
    return cases

if __name__ == "__main__":
    out = generate(sys.argv[1], sys.argv[2] if len(sys.argv) > 2 else "knowledge")
    with open("cases_generated.jsonl", "w", encoding="utf-8") as f:
        for c in out:
            f.write(json.dumps(c, ensure_ascii=False) + "\n")
    print(f"生成 {len(out)} 条，全部标记为待审")
```

生成完别急着高兴，审一遍你会发现大概一两条里就得扔一条：题面重复的、答案错的、还有那种文档里有但你的 Agent 根本没权限看的。剩下的按下面那四条标准过一遍，合格了再往对应的专项文件里放。

## 选题四条标准

一道题进不进题库，过我这套四问：

1. **覆盖真实场景吗？** 它是不是日志里真出现过的任务类型？如果没人会这么用你的 Agent，这题就是自嗨。
2. **难度有梯度吗？** 不能全是难题，也不能全是送分题。一条曲线：一部分它稳过、一部分它挣扎、一部分它基本过不了。没有梯度，你改完 prompt 都看不出变化在哪。
3. **能被客观判定吗？** 这是硬门槛。判不出来的题，先别进。T3 里那五个 benchmark 的共同套路就是把判定做成程序化的——查环境状态、精确匹配、跑测试——没有一条靠"看起来不错"。
4. **时间上稳定吗？** 这道题三个月后还能不能跑？如果题目依赖"今天的微博热搜"或者一个随时改版的网页，它是一次性筷子，用完就得扔。能进题库的题，判定所依赖的东西要么在沙箱里，要么你有把握它不变。

第四条我第一次是栽过的。出了道题让 Agent"查某产品价格并写入周报"，写得挺得意。一个月后复跑，那个网站改版了，接口全变，题废了，连带着那一批基于它结论的对比实验全部作废。别急，这类坑到 T9 讲非确定性时还会再踩一遍。

## 任务分层：清一色单轮问答测不出多步能力

攒够三十来道题之后，下一个动作是给它们分层。任务分层（Task Taxonomy，详见 TA 篇）听起来学术，其实就是打标签，四个维度：

- **任务类型**：检索问答 / 文档生成 / 数据汇总 / 发送执行……
- **复杂度**：单步 / 多步（3–5 步）/ 长程（10 步以上或带分支）
- **工具需求**：零工具 / 单工具 / 多工具组合
- **风险级别**：只读 / 可逆写 / 不可逆写（发邮件、删数据、下单）

打个样，周报助手的题库分层长这样：

```text
类型分布：  文档生成 40%  数据汇总 30%  检索问答 20%  发送执行 10%
复杂度：    单步 25%      多步 50%      长程 25%
工具需求：  零工具 10%    单工具 45%    多工具 45%
风险级别：  只读 50%      可逆写 30%    不可逆写 20%
```

为什么要这么麻烦？反例就是我的第一版题库：二十多道题，九成是单轮问答。周报助手在那个题库上 95 分，换到带工具、多步骤的真任务上原形毕露——它最弱的多步能力，我的题库压根没测到。

分层还有第二个用处：出分的时候能拆开看。总分 80 毫无意义，"不可逆写类任务成功率 55%"才是能拿去决策的数字。

## 难度分级别拍脑袋

"这道题挺难的"——多难？谁觉得难？拍脑袋标的难度，换一次人就变一次。用三个可数的东西标：

- **步数**：完成它需要几次工具调用。跑一次基准实现，数一数 trace。
- **歧义度**：指令里有几处需要 Agent 自己猜的地方。比如"发给相关的人"是一处歧义，"发给张三"是零处。
- **外部依赖数量**：它依赖几个你控制不了的东西（网页、接口、第三方数据）。依赖越多越难，也越不稳定。

三个维度各分三档，组合一下就是难度。不靠感觉，改 prompt 的人跟出题的人对"难"的理解也能对齐。

## 把题按专项拆成八类，别全塞进一个文件

分层打完标签，紧接着一个很土但很要命的问题：这些题放哪儿？

我最早就一个 `cases.jsonl`，从第一条堆到第二百条，从头堆到尾。堆到一百五的时候出事了：某次改完之后整体成功率掉了 6 个点，我盯着总分看了一下午，看不出是哪塌的。最后只能手动把题库切两半跑、再切、再切，靠二分法定位到是多轮那批题挂的。

这事儿麻烦就麻烦在，一个文件里的分数是个平均数，而平均数天生会掩盖结构变化。多轮掉 40 个点、单轮涨 15 个点，合起来可能只是"掉了 3 个点"，看着像噪声，实际上是塌了一角。

所以后来改成两层：**基础覆盖**打底，**专项探测**（Specialized Probe）各管一摊。基础那层回答"整体还能不能用"，专项那层负责把某一项能力单独拎出来往死里测。每个专项一个文件，各自配一组自己的指标——不是所有题都只看完成率：

| 评测集 | 构建方式 | 主要看什么 | 起步规模 |
|---|---|---|---|
| 基础能力集 | 按核心能力面构造，实时依赖用 mock（模拟桩）隔离 | 整体完成率、格式遵循 | ≥50 条 |
| 知识问答集 | 从自有文档抽问答对，含无答案 / 需降级 / 部分匹配 | 完成率、编造率、检索准确性 | ≥100 条 |
| 多轮对话集 | 构造 2–5 轮的对话链，含上下文引用、话题切换、指代消解（Coreference Resolution） | 多轮完成率、短时记忆保留 | ≥10 组 |
| 异常输入集 | 空输入、超长文本、乱码、特殊字符 | 异常输入处理率 | ≥20 条 |
| 工具调用集 | 按工具构造，正确 / 缺失 / 错误参数三类 | 工具选择准确、参数准确、调用成功 | ≥20 条 |
| 多意图集 | 一句话混 2–3 个意图 | 多意图识别率 | ≥20 条 |
| 模糊意图集 | 缺关键参数、指令不明确 | 是否主动追问澄清 | ≥20 条 |
| 长对话衰减集 | 5 轮以上，在第 2 / 3 / 5 轮插入需引用历史的追问 | 记忆衰减曲线 | ≥10 组 |

规模那列是"起步够用"的量，不是及格线，别当成标准答案抄。我开跑的时候基础题只有五十条，照样看得出问题。反过来你上来就堆五百条知识问答题，审核成本先把自己拖垮——每条都得有人看过答案才算数。什么时候加量？等你跑到发现"这个专项的题都太简单，两个版本区分不出差异"再说。

拆开之后的好处就两个，都很实在。

一是定位快。分数掉了，看一眼哪个专项文件掉的，就知道该去查哪块代码、哪段 prompt。不用再做我那套手动二分法。

二是省时间省钱。周报助手现在跑一次全量要四十分钟。改 prompt 的日子我根本不跑全量，只跑基础集加跟这次改动相关的那一两个专项，七八分钟出结果，token 钱也省下一多半。全量留给周末和要出结论的时候。

目录就这么摊着，一个文件一类，文件名即专项：

```text
evals/
  core.jsonl             # 基础能力集
  knowledge.jsonl        # 知识问答集
  multi_turn.jsonl       # 多轮对话集
  abnormal_input.jsonl   # 异常输入集
  tool_call.jsonl        # 工具调用集
  multi_intent.jsonl     # 多意图集
  vague_intent.jsonl     # 模糊意图集
  long_context.jsonl     # 长对话衰减集
```

这八类也不是什么标准分类，就是我按周报助手踩过的坑攒出来的。你的 Agent 不做多轮，多轮那组直接删；有别的弱项，自己加一类。分层是打标签，这是分文件，两件事，别混。

## 三个集合那点事

开发集、验证集、测试集（Dev / Validation / Test Set，详见 TA 篇）——传统 ML 课本里这三个各有严格分工：训练用不上测试集，调参用验证集，最后只碰一次测试集。

Agent 场景照搬这套会水土不服，因为**多数 Agent 场景根本没有"训练"**。你不 fine-tune 模型，你调的是 prompt、工具描述、流程。所以实际分工简化成这样：

- **开发集**：就是你调 prompt 时随手拿来试的那一小撮题。可以天天看，随便看。
- **测试集**：出正式分数的那批，平时锁起来，只在要出结论的时候跑。
- **验证集**：在这里基本就是"调参用的那一小撮"的正式说法——比开发集稍微规整一点，用来在动测试集之前做个中间检查。说实话，小团队里它和开发集经常就是同一批，这不丢人，知道自己在干什么就行。

真正要紧的规矩只有一条：**你调 prompt 时看过的题，跟最后打分的题，必须分开**。这条违反了，分数就不是分数了，是开卷考试成绩。

## 污染与泄漏：Agent 的污染长得不一样

数据污染（Data Contamination，详见 TA 篇）在 LLM 时代是个老话题：题被模型背过，分数虚高。到了 Agent 场景，污染多了几种新面孔：

**第一种，公开题被背过。** 最直接的。真实案例摆在这儿：SWE-bench Verified，2024 年 8 月由 OpenAI 和普林斯顿团队联合发布的 500 道人肉确认过的子集，一度是编码 Agent 评测的事实标准——**2026 年 2 月 23 日，OpenAI 宣布不再把它用于前沿模型评测，理由正是测试本身存在缺陷加上训练数据污染**。一个公认设计精良的评测集，从发布到被考烂，撑了一年半。你扒的那个公开题库，凭什么例外？

**第二种，环境变了。** 题没变，但题目依赖的网页内容变了、工具接口变了。这种污染最阴——分数掉了，你不知道是 Agent 变差了还是世界变了。前面我那个"查产品价格"的题就是死在这上面。

**第三种，自我泄漏。** 你调 prompt 用的题和测试集混在了一起。不需要模型背题，你自己亲手把答案泄露给了开发过程。这是我那个 91% 的真正死因——调 prompt 的时候我把整个题库翻来覆去看了几十遍，到打分时每一道题它都"恰好"表现很好。

**怎么查？** 一个朴素的办法：换同分布新题对小样本复测。拿一批模型不可能见过的题（自己新造的、日志里新捞的），抽样三十道左右跑一遍，看分数掉得离谱不离谱。掉 3–5 个点正常，掉 20 个点，说明原来的分数里有水分的占比不小。

## 动手产出：任务清单模板 + 去污染检查脚本

先给模板。一道题进题库，这些字段一个不能少：

```json
{
  "id": "weekly-report-017",
  "task": "汇总本周三组的项目进展数据，生成周报并发送给项目经理",
  "type": "文档生成+发送执行",
  "complexity": "多步",
  "tools_required": ["search", "read_doc", "send_email"],
  "risk_level": "不可逆写",
  "difficulty": {"steps": 5, "ambiguity": 1, "external_deps": 1},
  "source": "手工构造",
  "created_at": "2026-10-20",
  "last_verified_at": "2026-10-25",
  "split": "test",
  "expected": "见 T6 的 ExpectedOutcome 三段式"
}
```

注意 `last_verified_at` 这个字段——环境型题要定期重验，过期未验的题自动标记为存疑。

然后是去污染检查脚本。它干三件事：查开发集和测试集有没有重叠（自我泄漏）、查题面有没有跟公开语料高度撞车（外部污染）、查题的外部依赖是不是太久没验证（环境漂移）。纯标准库，能直接跑：

```python
# decontamination_check.py
# 用法：python decontamination_check.py cases.jsonl
import json
import re
import sys
from datetime import date, datetime
from difflib import SequenceMatcher

STALE_DAYS = 30  # 超过 30 天没重验的外部依赖题，标记存疑

def load_cases(path):
    with open(path, encoding="utf-8") as f:
        return [json.loads(line) for line in f if line.strip()]

def normalize(text):
    # 粗归一化：去空白和标点，小写
    return re.sub(r"[\s\W_]+", "", text.lower())

def similar(a, b, threshold=0.85):
    return SequenceMatcher(None, a, b).ratio() >= threshold

def check_split_leak(cases):
    """开发集/验证集与测试集题面撞车"""
    dev = [c for c in cases if c["split"] in ("dev", "val")]
    test = [c for c in cases if c["split"] == "test"]
    report = []
    for t in test:
        for d in dev:
            if similar(normalize(t["task"]), normalize(d["task"])):
                report.append(f"[SELF-LEAK] 测试集 {t['id']} 与 {d['split']} 集 {d['id']} 题面高度相似")
    return report

def check_public_overlap(cases, public_corpus_path=None):
    """与公开语料撞车（可选：提供公开题面清单，一行一条）"""
    if not public_corpus_path:
        return []
    with open(public_corpus_path, encoding="utf-8") as f:
        public_texts = [normalize(line) for line in f if line.strip()]
    report = []
    for c in cases:
        for p in public_texts:
            if similar(normalize(c["task"]), p):
                report.append(f"[PUBLIC-CONTAM] {c['id']} 与公开语料撞车，疑似被模型背过")
                break
    return report

def check_stale_env(cases):
    """外部依赖题超期未重验"""
    today = date.today()
    report = []
    for c in cases:
        if c.get("difficulty", {}).get("external_deps", 0) > 0:
            last = datetime.strptime(c["last_verified_at"], "%Y-%m-%d").date()
            if (today - last).days > STALE_DAYS:
                report.append(f"[STALE-ENV] {c['id']} 依赖外部环境，已 {(today - last).days} 天未重验")
    return report

if __name__ == "__main__":
    cases = load_cases(sys.argv[1])
    public_path = sys.argv[2] if len(sys.argv) > 2 else None
    findings = (check_split_leak(cases)
                + check_public_overlap(cases, public_path)
                + check_stale_env(cases))
    if findings:
        print("\n".join(findings))
        sys.exit(1)
    print("OK：未发现泄漏、污染或过期依赖")
```

拿一个样例 `cases.jsonl` 跑一下，输出长这样（故意埋了三处问题）：

```text
[SELF-LEAK] 测试集 weekly-report-017 与 dev 集 weekly-report-003 题面高度相似
[PUBLIC-CONTAM] gaia-adapt-002 与公开语料撞车，疑似被模型背过
[STALE-ENV] price-check-005 依赖外部环境，已 47 天未重验
```

把它塞进 CI，每次有人往题库里加题就跑一遍。防的不是黑客，是三个月后的你自己。

## 三十条起步够不够

够，也不够。

够的部分：三十条分层清晰、判定明确的题，足够暴露主要问题、足够支撑"这次改动有没有变好"的对比。比五百道没分层、判定模糊的题有用得多。

不够的部分：三十条样本量撑不起精确的百分比。成功率从 80% 到 84%，在三十条题上就是差了 1.2 道题，什么结论都得不出。真要比较两个版本的细微差异，那是 T11 置信区间篇要算的账。起步阶段的正确姿势是：**三十条题 + 每条跑多次 + 只看粗粒度结论**。先把架子搭对，再加题。

---

**一句话结论**：公开数据集是素材不是分数，变成自己的题要过四道关——分层打标签、难度用步数和依赖数标、开发集与测试集物理隔离、定期跑污染检查——那个曾经最权威的编码评测集就是没扛过最后一关。

**下一篇要解决的那个麻烦**：题有了，但每道题的"成功"还没定义清楚。下一篇《"成功"怎么定义》，把"答得还行"翻译成机器能判的三段式验收条件，附一个带 mock 邮箱的判定函数。
