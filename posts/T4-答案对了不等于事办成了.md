# 答案对了，不等于事办成了

草稿全对：三个来源都引了，每条带链接，正文 412 字，格式是我定的 Markdown。

它把这封邮件发给了 437 个人，包括 CEO 和三个外部客户。

正文第一句写着"以下是本周项目组内部数据汇总"。它自己知道是内部数据，标注得清清楚楚，然后按下了发送。

这次任务，算成功吗？

如果只判最终输出，它挑不出毛病，任何只看答案的脚本都会给满分。**所以 Agent 的成功必须判三层，而不是一层。**

## 一、三层判定：结果 / 过程 / 副作用

| 层 | 判什么 | 从哪取证 | 漏判的后果 |
|---|---|---|---|
| 结果层（Outcome） | 最终产物是否符合可核对的标准 | 产物本身：文本、文件、邮件正文 | 白干一场，但世界没坏 |
| 过程层（Process） | 该发生的步骤有没有真的发生 | 执行轨迹（Agent Trace，详见 TA 篇）里的工具调用 | 蒙对了你以为它会，下次就露馅 |
| 副作用层（Side Effect） | 它有没有做不该做的事 | 工具副作用留下的痕迹：信箱、数据库、文件系统 | 结果越漂亮，损失越大 |

多数人只判第一层，因为第一层好判：答案摆着，比一下就完事。过程层要翻轨迹，副作用层要查外部状态——麻烦，但躲不过去，因为 Agent 与纯 LLM 的本质差别就在这两层。

## 二、三种"答案对但没干成"

翻几十条运行记录，这类翻车只有三种形态，共同点是**只看最终答案全都判对**。

| 形态 | 典型表现 | 怎么发现 |
|---|---|---|
| 中间偷工减料 | 要求查三个来源，它查一个就开写，结论恰好蒙对 | 轨迹里工具调用次数对不上；产出与认真干活的长得一模一样 |
| 约束没满足 | 限 400 字写了 620、忘带附件、漏抄送 | 约束事先没写成数字，就永远发现不了 |
| 副作用失控 | 多发了人、删错了文件、调用了没授权的接口 | 只能查外部状态，答案里看不出来 |

第三种最贵，也最容易被"任务成功"掩盖——**它往往发生在成功的那一瞬间**，不是失败的副产品，而是成功路径上的一步。所以"任务成功没成功"这个问法，天生抓不到它。

## 三、副作用为什么排第一

因为另外两层错了还能重来，这一层错了不可逆。

邮件发了撤不回（Outlook 的撤回只在对方没读之前有效），数据删了找不回，单下了退款走三天，消息发错群截图已经传遍。

我那次的原因很蠢也很典型：它在内部文档里搜"项目组"，搜到一页过期通讯录，上面有 437 个地址，它没核对，直接全发。整个链路里没有一步叫"发送前确认收件人"。

## 四、一步一步把任务写成验收条件

这是这篇的动手部分。拿一个真实任务，按五步走，每步都要求"能取到证"。

**第 1 步：先写副作用层——用禁止句式。**

先问"它绝对不能做什么"，而不是"它应该做什么"。周报助手这层写完是：

```
不得向核准名单之外的地址发送；
发送次数必须等于名单人数；
不得调用 send_email 以外的任何写操作工具。
```

这一步放第一位，是因为它最容易漏，漏了代价最大。

**第 2 步：写结果层——每个条件都要能机检。**

把"内容准确、格式规范"换成："正文 300–500 字、至少 3 个可点击来源链接、文中数字与底稿一致"。

判据是：你能写出检查它的代码吗？写不出来就还没写完。

**第 3 步：写过程层——只标不可跳过的步骤。**

周报助手只需要两条：发送前调用过搜索至少 3 次；发送前调用过收件人核对工具。

**这一层最忌贪多**。标十条等于要求它照你的剧本演，换个更优路径就被判失败——那是测试你的路径，不是测它的能力。

**第 4 步：给每条约束补一个"取证来源"。**

在每条后面写清楚从哪读：`trace.tool_calls`、`mock_mailbox`、`db.orders`。写不出来源的约束，就是没定义。

**第 5 步：拿一条真实运行空跑一遍。**

用历史记录跑一遍判定，看三件事：有没有判不了的（说明取证来源不对）、有没有全过的（说明太松）、有没有明显冤枉的（说明约束写错了）。跑不通就回去改约束，别改 Agent。

**写不出来怎么办。** 第 2 步和第 3 步最容易卡住，三条降级路径按顺序试：

1. **换代理指标**："内容专业"换成"含 ≥3 个来源链接 + 无错别字 + 不超出字数区间"；
2. **降级人工抽查**：抽 10% 用例人工看，其余用代理指标，报告里标明抽查比例；
3. **删掉这条并记账**：明确写下"这条不判"，比写一条永远判不了的强——至少汇报时你知道自己在哪留了洞。

五步填完，一张表就出来了：

| 层 | 必填内容 | 周报助手的例子 |
|---|---|---|
| 结果层 | 可机检的产出标准 | 正文 300–500 字、≥3 个来源链接、数字与底稿一致 |
| 过程层 | 不可跳过的步骤（≤4 条） | 搜索 ≥3 次、发送前核对过收件人 |
| 副作用层 | 绝对禁止清单 | 只发核准名单、发送数 = 名单人数、不碰其他写工具 |

## 五、四条技巧

1. **判定顺序反着来**：先判副作用，再判结果，最后判过程。副作用最贵，早失败早止损；过程最便宜，放最后做归因。
2. **副作用层用"禁止"，不用"尽量"**。"尽量避免误发"没法判，"只发给名单内地址"能判。
3. **过程层不超过 4 条**。超过就是在测路径复刻。
4. **每条约束都必须有取证来源**。说不出从哪读，等于没定义——这条能筛掉九成的假验收条件。

### 我原来那份定义，问题在哪

原版写的是：*"生成一份本周项目进展周报，内容准确，格式规范，发送给项目组。"*

三句话，三处没法判："内容准确"谁说了算、"格式规范"哪份规范、"项目组"是谁——它确实发了，发给了它自己认定的 437 人。

改成三层之后多写了两行，就这两行，拦下了后面几乎所有的翻车。

## 最后

Agent 的成功条件要写成三层：结果对、过程走过、没出副作用。只判最后一层答案，等于把最致命的那类失败设成满分。
