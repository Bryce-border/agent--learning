# 答案对了，不等于事办成了

周报助手回我的那封草稿，内容全对：数据来源引用了三个，每条都带链接，字数卡在 400 字以内，格式是我定的 Markdown。

唯一的小问题：它把邮件发给了全公司 437 个人，包括 CEO 和三个外部客户。

正文第一句本来写的是"以下是本周项目组内部数据汇总"。内部。它自己也知道是内部数据，引用标注得清清楚楚，然后它把这封信，真的，发出去了。发给所有人。

请问：这次任务算成功吗？

## 我当时是怎么回答的

我盯着那个"已发送"看了大概有十秒钟，脑子里第一个想法居然是："正文写得真不错。"

第二个想法才是冷汗。

这事儿烦就烦在，如果你只盯着最终输出看，它挑不出任何毛病。引用对、格式对、字数对、内容准确。任何一个只看答案的评测脚本都会给它打个满分。但它造成的后果是——我接下来两个小时在写道歉邮件和找 IT 问能不能撤回。撤不回，Outlook 的撤回功能只在收件人没读之前有效，而 437 个人里总有手快的。

（后来才知道，它选收件人的逻辑是：在内部文档里搜"项目组"，搜到一页过期的通讯录，上面有 437 个人的地址。它没有一个一个核对，直接全发了。）

这就是我后来给评测体系加的那一整层的来历。

## 两层判定：结果对了，过程呢

把评测拆成两层，是最起码的一步：

- **Outcome（结果层）**：最终输出的东西对不对。周报内容准不准、格式对不对、字数超没超。
- **Process（过程层）**：它是怎么走到这个结果的。该查的来源查了没有、该核对的收件人核对没有、中间步骤有没有偷工减料。

多数刚跑通 demo 的人——包括当时的我——只判了第一层。原因是第一层好判：答案摆在那儿，比对一下就行。过程层麻烦，你得去看它的执行轨迹（Agent Trace，详见 TA 篇），一步一步翻它调了什么工具、传了什么参数。

麻烦，但躲不过去。因为 Agent 跟纯 LLM 有一个本质差别。

## 多出来的那条命：副作用撤不回

纯 LLM 答错了，代价是什么？一段废话。你看一眼，关掉，重开一问，损失为零。这就是为什么 T2 里说过"LLM 评测和 Agent 评测不是一回事"——这里把那条差别真正坐实。

Agent 不一样。它的工具会产生**不可逆副作用（Irreversible Side Effects，详见 TA 篇）**：

- 发出去的邮件，撤不回
- 删掉的数据，找不回
- 下单的钱，退不掉（或者能退，但流程走三天）
- 发错群的消息，截图已经传遍

说白了，LLM 写错一行字，世界是干净的；Agent 点错一次"发送"，世界被它改了。

这意味着一件事：对 Agent 来说，"过程"和"副作用"是比"结果对错"更致命的东西。结果错了顶多白干，副作用错了是倒贴。我那封发向全公司的邮件，内容越漂亮，越是精准地把内部数据投给了不该看的人。

## 三种"答案对但活没干完"

翻完几十条周报助手的运行记录，我把这类翻车归成三种。三种的共同点：只看最终答案，全都判对。

**第一种：中间步骤偷工减料。**

任务要求"查三个来源交叉验证"。它查了第一个，发现信息够写一段了，后两个来源直接跳过，结论恰好蒙对。答案对，但"交叉验证"这个要求根本没执行。哪天第一个来源出错了，你一点察觉的机会都没有——因为它从来没备过后手。

这种最难发现，因为它的产出和认真干活的产出**长得一模一样**。区别只在 trace 里：工具调用次数对不上。

**第二种：约束没满足。**

字数上限 400，它写了 620；要求带附件，没带；要求抄送项目经理，漏了。正文内容本身没问题，可任务的一部分压根没做。

这类好判，只要你事先把约束写下来——问题是多数人没写。"周报别太长"不是一条能判定的约束，"正文 300 到 500 字"才是。怎么写是下一篇 T6 的事。

**第三种：副作用失控。**

多发了（给不该收到的人）、删错了（清理草稿时把正式邮件删了）、调用了不该调的工具（为了"查数据"去访问了没授权的接口）。我那 437 个人的惨案就属于这类。

这类有个特征：**它往往在任务"成功"的那一瞬间发生**。它不是失败的副产品，它就是成功路径上的一步。所以只看"任务成功没成功"，永远抓不到它。

## 为什么我们本能地只看答案

想清楚一件事：只看答案这个毛病，不是你粗心，是有历史原因的。

过去两三年，我们被 LLM 评测训练出了一套肌肉记忆——给模型一段输入，看它一段输出，比对，打分。整套产业工具都长这样：排行榜比的是分数，demo 展示的是最终回答，连验收 demo 的老板也只看你贴出来的那段文字漂不漂亮。这套习惯搬到 Agent 上，每一步都还是熟悉的动作，只是每一步都开始漏东西。

我也这么以为过。跑通周报助手的第一周，我的"评测"就是把它的输出截图发到群里，配文"你们看，写得还不错吧"。下面一排点赞。没人问它查了几个来源，更没人问它发给谁了——我自己也没问，直到那 437 个人替我问了。

盯着答案看，本质是评审成本最低的选择。而 Agent 这个东西，恰恰把最贵的部分藏在了答案外面。

## 先错后对：我原来的成功定义

我之前给周报助手写的成功条件，原文是：

> 生成一份本周项目进展周报，内容准确，格式规范，发送给项目组。

现在回头看，这条定义约等于没写。"内容准确"怎么判？"格式规范"谁来定？"发送给项目组"——它确实发送了，发给了 437 个人组成的、它自己认定的"项目组"。

改完之后的版本长这样：

> **结果**：收件箱中出现一封正文 300–500 字、含三个以上可点击来源链接、无虚构数据的邮件。
> **过程**：邮件发送前，调用过搜索工具至少 3 次，且调用过收件人查询工具核对收件人名单。
> **副作用**：仅且仅向核准名单中的地址发送，总发送数等于名单人数，未调用任何名单外工具。

多写了两行。就这两行，拦下了我后来遇到的几乎全部的翻车。

## 成功条件三层检查表

动手产出就这张表。每给 Agent 定义一个任务，把三层各填一遍，有一栏空着就别跑：

| 层 | 问自己的问题 | 周报助手的例子 |
|---|---|---|
| 结果层 | 最终产出要满足什么可核对的标准？ | 正文 300–500 字、≥3 个来源链接、数据与来源一致 |
| 过程层 | 哪些步骤必须真的发生？怎么从 trace 里看出来？ | 搜索调用 ≥3 次、发送前调用过收件人核对工具 |
| 副作用层 | 它绝对不能做什么？做了什么算事故？ | 只发给核准名单、发送次数 = 名单人数、不碰名单外工具 |

填的时候有个小技巧：每一层都逼自己写成"能用程序判"的形式。写不出来的——比如"内容要专业"——先留着，T6 专门处理这种话。

还有一点容易被忽略：副作用层不是"可选项"。只要你的 Agent 有一个能改变外部世界的工具，这层就必须填。哪怕任务再小。"把文件整理一下"这种任务，副作用层也要写"不得删除任何原文件"。

## 下一篇的麻烦

知道要判三层了，真坐下来写，你会发现另一件事——自己平时挂在嘴边的"答得还行""写得挺专业""格式看着没问题"，没有一条能变成判定代码。

我当时写第一版检查表，结果层填的是"周报质量高"。对着这一行看了五分钟，一个问题都问不出来。质量高是高多少？谁说了算？

标准怎么写到"可判定"，是 T6 的活。但标准得有题来配——你的题从哪来？公开数据集直接抄行不行？那是紧挨着的下一篇。

---

**一句话结论**：对 Agent 来说，评测要判三层——结果对不对、过程走没走、副作用出没出——只看最终答案的评测，等于把最致命的那类失败设成了满分。

**下一篇要解决的那个麻烦**：判三层需要题，题从哪来？公开数据集能不能直接用？下一篇《把公开数据集改成自己的》，讲怎么把别人的素材改成能给你 Agent 打分的题，以及为什么 SWE-bench Verified 会被考烂到停用。

**踩坑征集**：你的 Agent 干过"答案全对但事没办成"的事吗？发错人、删错文件、重复下单都算。评论区说说，我挑几个典型的收进翻车合辑 F2。
