# 为什么两次跑出来不一样：代码一行没改，80% 变成 72%

周五下午五点，周报助手跑完 30 道题，成功率 80%。

我挺满意，关机回家。周一上午手贱又跑了一遍——同样的代码、同样的任务集、同样的模型，72%。

git log 是空的，一个提交都没有。

这不是玄学，也不是模型在跟你开玩笑。评测 Agent 跟评测普通程序最大的区别就在这儿：普通程序同一份输入跑一百次是一百个相同的结果，Agent 不是。你要是一直默认它是，后面所有"改了之后变好了"的结论都站不住。

这篇把波动的来源数一遍，聊聊固定 seed 到底能不能固定住（先剧透：多数商用模型不行），给一份运行快照模板，最后讲怎么把"波动"和"你改动带来的真实差异"分开。

## 五个来源，一个一个认

**① 采样参数：temperature 和 top_p。**

这个第一个被怀疑，也经常被过度怀疑。temperature 大于 0 时，模型每一步都在做带随机性的采样，多步 Agent 会把这个随机性逐级放大——第一步偏一点，第二步基于偏了的结果再偏一点，五步之后可能走到完全不同的路上。

先把它设成 0 试试。设完波动还在，那就不是它的锅。

**② 并发与执行顺序。**

同一个任务集，用 `max_workers=4` 跑和串行跑，结果可能不一样。原因通常有两个：一是你的 Agent 有"多路检索再合并"的逻辑，合并顺序变了结论就可能变；二是共享了可变状态——上一篇那个全局 `SENT_MAILBOX` 就是个现成的雷，并发下它会串味。

**③ 外部工具超时。**

超时是一个概率事件，取决于网络、对方服务当时忙不忙。上一次 8 秒返回，这一次 60 秒还没回，判定结果就从"成功"变成"timeout after 60s"。这类波动最容易被误读成能力波动，其实它反映的是依赖的稳定性（详见 T22 的故障注入）。

**④ 外部数据变化。**

网页改版、内部文档更新、数据库里多了一批记录。这一条最阴，因为它是单向漂移，会伪装成"版本变好了"或者"版本变差了"。

周报助手在这上面栽过：它查"上周销售数据"，周五查和周一查，这个"上周"指的是两个不同的时间段。同一份代码、同一个 prompt，周一跑出来的数字就是不一样，而且你没法靠多跑几次消掉它——它每次都在往同一个方向偏。

**⑤ 模型服务端的版本漂移。**

你调的是 `YOUR_LLM_ENDPOINT`，那边的服务升了个小版本、换了个推理框架、调了负载均衡策略，不会通知你。外面看起来模型 ID 一个字没变，行为已经悄悄不一样了。

这五条里，①②③让结果上下抖动，④⑤让它整体平移。抖动可以靠多跑几次摸清，平移不行——这就是为什么后面要记录环境快照。

## 固定 seed 能不能真的固定？

先给结论：对多数商用模型 API，不能。我知道这句话让人不舒服，但给虚假的安全感更糟。

seed 这个参数（如果服务端支持的话）保证的是一件事：采样过程用的伪随机数序列起点一致。可最终输出还受别的东西影响——

- 服务端把哪些请求凑成一个 batch 一起算，而 batch 的组成你控制不了
- MoE 架构下的专家路由选择
- GPU 上浮点运算的非结合性，同一个矩阵乘法换个切分方式结果就有末位差异，多步下来被放大
- 底层 kernel 版本、驱动版本
- 你的请求被打到哪台机器上

我当时也这么以为：设个 `seed=42` 就万事大吉了。后来同一份脚本连着跑两次，结果还是不一样，我才去认真查这件事。

那 seed 还设不设？设，但要知道自己在设什么。

它在两种情况下是真的有用的：一是你全链路自己控制——本地部署的开源模型、固定版本的推理框架、单卡、固定 batch size，这种条件下 seed 是可靠的，**Reproducibility（可复现性）**（详见 TA 篇）能真正做到；二是给自己托底，把能固定的先固定掉，减少波动源的数量，哪怕归不了零。

判断方法很土：设上 seed，同一批任务连跑 3 次，看结果是否**完全一致**。只要有一次不一致，就当它不能固定，然后在报告里如实写"已设 seed，但未观察到完全可复现"，别写"已固定随机性"。这两句话的差别，是有人会拿你的报告去做上线决策的。

## run metadata：缺一项，复盘就断线

周五 80%、周一 72%，你想查清楚到底差在哪。这时候手上有什么？

如果只有一张 CSV，那你什么也查不出来。所以每次运行都要留一份环境快照，我现在的格式是这样：

```yaml
# runs/20261024-173000-wr-v3.meta.yaml
run_id: 20261024-173000-wr-v3
started_at: 2026-10-24T17:30:00+08:00
finished_at: 2026-10-24T17:34:12+08:00

code:
  git_commit: a1b2c3d
  dirty: false              # 有未提交改动必须写 true，别偷懒
  script: eval_min.py

model:
  provider: YOUR_PROVIDER
  model_id: YOUR_MODEL_ID
  version: YOUR_MODEL_VERSION   # 别只写 model_id，厂商常给 minor version
  temperature: 0.0
  top_p: 1.0
  seed: 42
  seed_effective: false         # 上面验证过没用就如实写 false

runtime:
  python: 3.11.6
  deps: {requests: "2.32.3", YOUR_DEP: "x.y.z"}
  max_workers: 4
  timeout_s: 60

dataset:
  file: testcases.jsonl
  sha256: YOUR_SHA256
  count: 30

external:
  internal_doc_snapshot: 2026-10-24
  search_engine: YOUR_SEARCH
  db_synced_at: 2026-10-24T09:00:00+08:00

results:
  csv: runs/20261024-173000-wr-v3.csv
  task_success_rate: 0.80
  p95_latency_s: 57.6

notes: "周五跑的，业务库当天上午刚同步完"
```

几个容易漏又特别要命的字段：

- `model.version`——只写 model_id，等厂商悄悄升了小版本你就是那个查不出原因的人。
- `dataset.sha256`——任务集偷偷改过一道题然后忘了，是"我什么都没改啊"最常见的真相。
- `code.dirty`——true 意味着有未提交改动，等于这次结果不可复现，得标出来。
- `external` 那一整块——它是外部数据漂移类问题的唯一线索。没记，就等于放弃了排查④这条路径。

用法上就一条规矩：meta 文件和 results.csv 成对出现，放在同一个目录，少一个就算这次运行没发生过。文件名的 `run_id` 用时间戳打头，排序就是时间序。

## 两条路：把工具锁死，还是全真放跑

回头看上面③和④，根子都在外部世界：工具会不会超时、数据有没有变。既然抖动的大头在这儿，一个很自然的念头就冒出来了——那就把它锁死呗。

问题是，锁死之后你测的还是不是那个 Agent。

**真实性（Realism）**和可复现性这两件事，是打架的。你要真实，就得接受外部世界今天的样子，包括它今天抽风；你要可复现，就得把外部变量按住，那它就不是真实世界了。说白了，没有两全的方案，只有两套分开跑的评测模式，各答各的问题。

我现在就是把评测切成两套，从来不混。

**模式一：Mock 模式（把工具返回锁死）。**

预先给每个工具备好固定的返回值。Agent 跑到要调工具那一步，拦截器把真调用拦下来，把预设值丢回去。

注意锁的是哪一层：**Agent 的推理和决策全是真的，只有外部世界是假的。**该查什么、该不该发邮件、正文怎么写，还是它自己一步步想出来的，一步没省。

好处很直接：外部依赖的抖动被彻底关掉了。同一条用例，今天跑和下周跑，结果一致。哪条挂了，你把 mock 数据一挂就能复现，不用去猜"那天人家接口是不是刚好在维护"。

适用的是那类依赖实时数据的任务。周报助手查"上周销售数据"就是典型——不锁的话，测试失败你根本分不清是 Agent 没搞对，还是数据源自己变了。我当时想岔了，头两天一直以为是自己 prompt 写崩了，翻来覆去地调，最后才发现是"上周"这个时间段指向变了（就是④那条）。两天，全搭进去了。

mock 数据我按用例 id 组织，一个用例一份：

```json
{
  "case_id": "wr-007",
  "mocks": {
    "query_sales": {
      "range=last_week": {
        "rows": [{"region": "华东", "amount": 1204000}],
        "as_of": "2026-10-24"
      }
    },
    "send_mail": {"status": "sent", "msg_id": "YOUR_MSG_ID"}
  }
}
```

拦截本身也就几行：

```python
def call_tool(name, args, *, mode, case_id):
    if mode == "mock":
        key = f"{name}:{json.dumps(args, sort_keys=True)}"
        return MOCK_BANK[case_id][key]      # 命中不了就直接抛错，别悄悄兜底
    return real_call(name, args)

resp = llm_client.chat(messages, tools=TOOLS)   # llm_client 换成你自己的
```

那个"命中不了就抛错"是故意的。要是静默放它走真实调用，你会以为自己在 Mock 模式，其实一半请求已经跑到线上去了，数据看着还挺正常。

**模式二：真实模式（全链路真跑）。**

真模型、真工具、真检索，什么都不替。

好处不用讲，这才是用户实际会遇到的东西。

代价是结果会被外部抖动污染：工具偶发超时、数据源刚好落在更新窗口里、模型输出本身带随机性，全都混进那个百分比里。所以真实模式的数字，得多跑几次才有意义（跑几次是下一节的事）。

它有个不可替代的用处：**当你要验证的正是检索这条链路本身好不好使的时候，必须真跑。**

这里有个特别容易掉的坑。如果你的验证对象就是检索链路，你却把检索的返回给 mock 掉了，那这场评测等于什么都没测。mock 数据等于直接把标准答案塞进 Agent 手里，你测出来的是"它拿到正确资料之后能不能写好周报"，不是"它能不能查到正确资料"。这两个分数差多少？我这边差过二十多个点。而差的那部分，恰恰是你做检索优化最想知道的东西。

**Mock 模式下的"参考输出"，别写具体内容。**

这条反直觉，但我觉得是 Mock 模式里最容易写错的一处。

用例里的参考输出不该写成具体内容，只该描述 **Agent 应该有怎样的行为、输出长什么样**：

```json
{
  "case_id": "wr-007",
  "expect_behavior": {
    "intent": "send_weekly_report",
    "must_call": ["query_sales", "send_mail"],
    "output_structure": {"has_summary": true, "has_next_week_plan": true}
  }
}
```

不要写 `"expect_text": "上周华东区销售额 120.4 万元……"`。

道理是这样的：Mock 模式已经保证了工具会返回什么，输入是确定的。Agent 只要把路走对——识别意图 → 选对路径 → 调对工具 → 生成结果——基于确定的输入，自然会产出合理的内容。这时候再去卡它具体怎么措辞，等于把"流程走没走对"和"话怎么说"两个问题搅到了一起。分数掉了，你不知道该去改编排逻辑，还是该去调 prompt 的语气。两个问题挤成一个分数，那个分数就没用了。

至于内容的准确性——有没有编数字、该覆盖的知识点覆盖没有——那是另一类评测集的活儿，跟流程评测分开做。混着做我试过，那阵子的复盘会开得格外难受。

**怎么选：**

| 你要验证的东西 | 用哪套 | 原因 |
|---|---|---|
| 意图识别、工具选择、流程编排 | Mock | 外部抖动不该参与判定 |
| 依赖实时数据的端到端流程 | Mock | 不然失败归因说不清 |
| 检索 / 查资料这条链路本身 | Real，必须 | mock 掉等于没测 |
| 内容的事实准确性、覆盖率 | Real | 准确性得跟真数据比 |
| 版本 A/B 对比、回归防倒退 | Mock | 波动小才看得出两三个点的差 |
| 上线前最终验收 | Real | 用户面对的就是真实世界 |

一句话：平时迭代用 Mock，发布前拿 Real 兜一遍。两套都跑，但别拿一套的分数去回答另一套的问题。

## 多少次算够

不是越多越好。这事儿烦就烦在，很多人一拍脑袋说"那就跑 10 次"，跑完发现账单是原来的十倍，而且还是不知道该说啥。

看你要回答什么问题：

| 你要回答的问题 | 每任务重复次数 | 任务数 | 你最多能说的话 |
|---|---|---|---|
| 粗筛：这版本大概行不行 | 1 | 20–30 | "大概在 60%–80% 这个量级" |
| 迭代：改了 prompt 有没有变好 | 3 | 30–50 | "两版差 5 个点，看着像是真的"（严格判定见 T11） |
| 上线决策：能不能放出去 | 3–5 | 50–100 | "成功率 X%，跨次波动 ±Y" |
| 对外汇报 / 写进材料 | 5 | 100+ | "X%（95% 置信区间 A–B，n=100，重复 5 次）" |

表里那个 **Confidence Interval（置信区间）**（详见 TA 篇）是 T11 的地盘，这里提前提一句只是想说明：光秃秃的百分比撑不住追问，得带上样本量和口径。

注意"重复次数"指的是每个任务跑几次，不是跑几轮完整评测。30 道题 × 3 次 = 90 次 Agent 运行，成本自己乘一下。这也是别一上来就 5 次的原因——先把任务数堆到 50，再考虑加重复次数，性价比通常更高。

还有个反直觉的点：**跨次波动本身就是个指标**。30 道题跑 3 次，成功数分别是 24、19、23，这个 stddev 就是 **Inter-run Variance（跨次运行波动）**（详见 TA 篇）。在动手对比两个版本之前先看它——如果它已经大到 5 个点，那 82% 和 84% 这种差异根本没有讨论价值，先回去解决稳定性。

## 控制变量：把波动和真实差异分开

这是本篇最实用的一块，也是我踩过最贵的坑。

原则一句话：你只想知道 A 和 B 两个版本的差，那就别让别的东西也跟着变。

四条具体做法：

**同一批任务。** 对比期间别往任务集里加题改题，改了就得把两边都重跑。上面那个 `dataset.sha256` 就是为这条服务的。

**同一时间段。** 两个版本尽量挨着跑，最好在同一小时内。隔一周再补跑基线的话，"上周""最新""当前"这类词的语义已经变了，你测的就不是同一个东西了。

**同一版本依赖。** Agent 依赖的库、工具服务的 schema、内部文档的快照，全固定住。依赖版本写进 `runtime.deps` 不是为了好看，是为了这条。

**并发与顺序一致。** 顺序敏感的逻辑（比如合并多路检索结果）在对比时必须固定 `max_workers`。拿不准到底敏不敏感的时候，把它设成 1 跑一轮，用这个结果回答"顺序是不是个因素"。

说个我自己的翻车：改完 prompt 立刻重跑，成功率从 72% 涨到 81%，我兴冲冲记进周报。三天后才知道，那两天内部文档系统正好做了一次索引重建，检索命中率整体上去了，跟我的 prompt 一点关系没有。9 个点里有多少是我的功劳，永远说不清了。

那次之后我养成的习惯是：**改完立刻跑，别攒到周末一起跑。** 攒着的代价就是外部环境替你做了一次不可控的对照实验。

还有个便宜又好用的技巧——交错跑（interleaving）。同一个任务按 A、B、A、B 的顺序交替执行，而不是先跑完 30 道 A 再跑 30 道 B。这样环境漂移会平均摊到两边，而不是全算在后跑那个版本的账上。这个思路在 T22 做故障注入时也用得上。

别急，这里没有"彻底消除波动"的方案。有的只是把波动测出来、记下来、然后在对比时让它别捣乱。

## 一句话结论

Agent 评测里不存在"跑一次得到 80%"这回事，存在的只有"在某个环境快照下、某批任务上、某个时间窗口内，得到了 80%"。

下一篇要解决的麻烦很直接：既然波动不可避免，那"跑一次得到 80%"这句话本身就没意义了——T10 讲怎么把重复运行的结果算成 **Pass@k（多次尝试中至少一次成功的概率估计）**和 **Pass^k（多次尝试均成功的概率估计）**（均详见 TA 篇），这俩数能差出三十个点，别再混着报。再往后的 T11 才回答那个最扎心的问题：82% 和 84%，到底谁更好。

你的 Agent 两次跑出来最多差过多少？尤其是那种最后查出来原因特别离谱的——我这边最离谱的一次是 DNS 缓存，排查了整整两天。评论区说说，攒够一批我写进番外 F2 的错题本。
