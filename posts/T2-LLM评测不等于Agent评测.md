# LLM 评测 ≠ Agent 评测：多出来的四样东西

周报助手把上周的汇总邮件发给了全公司，抄送栏还挂着一个外部合作方的邮箱。正文一个字都没错——数据交叉核对过，格式合格，引用齐全，按 LLM 评测（LLM Evaluation，详见 TA 篇）的规矩该判满分。可那封邮件撤不回来。

这就是分界线：评 LLM 的那套方法搬到 Agent 身上，会漏掉四样东西。每漏一样，你都会拿到一个"看起来挺好"的结论。

## 一、多步骤：中间错一步，最后怎么都是错

LLM 评测的基本单元是一来一回：一条 prompt 进去，一段文本出来。

Agent 不是。一句"写周报并发给张三"，内部是这么一串：判断要不要搜 → 搜什么词 → 点开哪三个链接 → 每篇抽哪几段 → 两个来源数据打架时听谁的 → 按什么结构写 → 发给谁 → 要不要抄送。

**每一步都能单独出错，而且错误会累积。** 串行十步，单步成功率 95%，整体只剩 60%（0.95¹⁰ ≈ 0.599）；单步 90%，整体 35%。模型没变笨，是它现在得连着对十次。

只看最后那段输出，会漏掉两类失败：

| 失败形态 | 按终态判 | 实际情况 | 下次会怎样 |
|---|---|---|---|
| 要求查三个来源，只查了一个，恰好数据齐全 | 满分 | 偷工减料 | 那个来源一没更新就瞎 |
| 中间 JSON 解析失败，拿半个结果凑出结论 | 扣分 | 错在解析，不在写作 | 改 prompt 永远改不好 |

**对应的做法**：每次工具调用的名称、参数、返回、耗时全部落盘（Trace，详见 TA 篇），判定时既看终态，也看关键步骤有没有真的发生。

## 二、工具副作用：错了撤不回来

LLM 的输出是文本，不满意扔掉，代价为零。Agent 会真的动手：发邮件、下单、改库、删文件、提 PR。其中相当一部分是不可逆副作用（Irreversible Side Effect，详见 TA 篇）。

我最早栽的就是这个。答案那一栏满分，副作用那一栏负分，而且没法撤销。

**对应的做法**：不可逆操作一律在受控环境里跑——假邮箱、沙箱订单、数据库副本。这不是"建议"，是前提：不这么做，评测本身就会变成生产事故。

有个反直觉的点：mock 掉之后分数会变好看，那是好事。因为你终于能把"做对了没有"和"真的做了没有"分开看。

## 三、环境不确定：同一个输入，两次两个结果

早上跑成，下午跑挂，代码一行没改。原因可能是：要抓的网页中午改版了、搜索接口 503 了、接口还在但 JSON 少了个字段、模型服务端换了版本。

LLM 那边也有随机性（temperature 不为 0 时输出会变），但影响有限——输入自足，模型闭着眼睛也能答。Agent 每跑一步都在跟一个会变的外部世界打交道。

我第一反应是"模型今天变笨了"。翻 Trace 才发现，第二步搜索 503，模型拿到空结果，自己做主编了两段看着挺像的上周数据填进去。

先错后对，修正一下：**问题不在模型，在它没有能力区分"查到了空"和"查不到"。**

**对应的做法**：外部依赖能 mock 就 mock，换来可复现；但如果验证对象本身就是检索链路，就不能 mock，只能真跑并接受波动。这条分界线 T9 会展开。

## 四、评价对象变了：从一段文本，变成三层

前三条汇总起来，就是第四条。

评 LLM，你手上能被验证的只有一段文本。评 Agent，有三样：

- **一段过程**：走了哪几步，哪一步掉的链子
- **一个终态（End State，详见 TA 篇）**：事情办完，世界变成了什么样
- **一堆副作用**：除了目标动作，它还顺手做了什么

三样得一起看。只看终态，会漏掉蒙对的；只看过程，会奖励"步骤规范但没办成事"的；不看副作用，会给那封群发邮件打满分。

所以判定不能合成一个总分，三个字段分开返回：

```python
def judge(task, trace, mailbox):
    want = set(task["expected"]["recipients"])
    got = {m["to"] for m in mailbox.sent}          # 终态：假信箱里躺着几封
    searched = "search" in [s["name"] for s in trace["steps"] if s["type"] == "tool"]
    return {
        "end_state_ok": want == got,               # 该发的都发了
        "process_ok": searched,                    # 该查的查了
        "side_effect_clean": not (got - want),     # 没多发人
    }
```

合成一个总分，你就又回到"看着还行"了。

拿开头那次群发跑一遍，返回的是这个：

```json
{"end_state_ok": false, "process_ok": true, "side_effect_clean": false}
```

三个字段一起看，故事才完整：过程是对的（它确实查了资料），终态不对（该发的人没发全），副作用脏了（多发了全公司和外部邮箱）。要是合成一个 0.33 的分数，你既不知道该改哪，也没法跟老板解释这 0.33 是什么。

说白了，**三层判定的价值不在分数，在于它直接指向下一步动作**：终态错 → 改任务理解或工具；过程错 → 改规划；副作用脏 → 加权限和确认。

如果时间只够测两样，先测终态和副作用。过程那层等真出了问题再补——因为没有过程记录你照样能发现"没办成"，但没有副作用检查，你可能连"办了不该办的"都不知道。

### 一张表把差别钉死

| | 评 LLM | 评 Agent |
|---|---|---|
| 输入 | 一条 prompt | 一个任务 + 一套工具 + 一个环境 |
| 输出 | 一段文本 | 过程 + 终态 + 副作用 |
| 能验证的东西 | 文本本身（比对参考答案 / 裁判打分） | 终态查状态、过程看 Trace、副作用看工具记录 |
| 失败长什么样 | 答错、答偏、废话多 | 中间某步错、做了不该做的、环境一变就崩 |
| 重跑一次 | 大致一样 | 可能完全不一样 |
| 搞砸的代价 | 文本扔掉即可 | 可能撤不回来 |
| 判定难点 | 开放式输出不好判 | 三层要分开判，而且各自都得能解释 |

## 五、这四样让评测贵在哪

| 多出来的东西 | 谁在涨 | 怎么涨 |
|---|---|---|
| 多步骤 | Trace 的存储、检索、可视化 | 每步都要落盘，量级按步数乘 |
| 工具副作用 | mock 层或沙箱 | 一次性投入，通常是整个评测里最贵的一块 |
| 环境不确定 | 重复运行次数 | 单次结论不可信，成本 × k |
| 三层判定 | 判定器数量 | 一份变三份，还得各自能向人解释 |

合起来就是那个估算式：**单次运行成本 × 重复次数 + 一次性环境建设**。T1 说"精度是按场景买的"，买的就是这两个因子。

## 六、拿这四条去审别人的结论

下次有人跟你说"我们 Agent 准确率 90%"，问四句：

1. 这条链路要连着对几步？单步成功率是多少？
2. 不可逆操作在什么环境里跑的，真环境还是 mock？
3. 跑了几次，报的是最好一次还是平均值？
4. 判定看的是终态、过程，还是只看它自己写的那段话？

四问里有两个答不上来，这个 90% 就不能拿去决策。按左列算出来的 90%，多半只覆盖了"文本写得对不对"，剩下三样它压根没测——那不是 90 分的 Agent，那是 90 分的作文。

### 这四样对应后面哪些篇

- **多步骤** → 得能回看它走过的路，所以有 T19（看 Trace 破案）；得单独看它工具调得对不对，所以有 T21（工具调用评测）
- **工具副作用** → 得划清哪些事不许它自己做，所以有 T24（安全边界）；得让工具能被假装弄坏，所以有 T22（故障注入）
- **环境不确定** → 得控制变量、得重跑、得算方差，所以有 T9 和 T10
- **评价对象变成三层** → 成功的定义得写成"结果对、过程对、没出事"，所以有下一篇 T4

说实话，如果 Agent 跟 LLM 一样只吐文本，这个系列写到 T2 就可以收工了。

---

**一句话结论**：LLM 评测评的是一段文本，Agent 评测评的是"它做了什么、做成了没有、还顺手干了什么"。这三样东西叠在一起，才让评测从"打个分"变成一整套工程。

**下一篇要解决的那个麻烦**：道理讲完了，具体怎么出题、怎么判定还是没谱。这时候最划算的一步，是先看别人花了几个月做出来的题长什么样——下一篇把 GAIA、AgentBench、WebArena、τ-bench、SWE-bench 五个 benchmark 逐个拆开，看它们各自在测什么、判定做在哪一层。

**踩坑征集**：你的 Agent 干过最离谱的"不可逆操作"是什么？真发邮件、真删表、真下单都算。报过来，最惨的那几个我放进 T24 讲安全边界那篇当反面素材。
